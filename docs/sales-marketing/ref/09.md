# Phase 09: Audience Segmentation and Targeting

## 1. Objective

Implement a production-ready, secure, reusable **Audience Segmentation and Targeting** capability within the existing Sales & Marketing module.

The feature must allow authorized users to define, preview, manage, and maintain marketing audiences using configurable criteria based on existing CRM and other approved business data sources. Segments must be reusable across marketing campaigns and designed to integrate with future marketing channel execution without implementing that execution in this phase.

This is an **industry-agnostic ERP feature**. Do not introduce garment-, textile-, manufacturing-, or any other industry-specific assumptions, entities, fields, workflows, or terminology.

The goal is to build a reliable audience segmentation engine, not a duplicate CRM, customer database, consent management system, or marketing automation platform.

4. Reuse existing services, models, components, and infrastructure wherever possible.

## 4. Audience and Segment Management

Provide a segment management interface and backend services for creating, viewing, editing, duplicating, archiving, and evaluating segments.

Each segment should support applicable fields such as:

- Name.
- Unique code or identifier, following existing repository conventions.
- Description.
- Segment type: dynamic or static.
- Status: draft, active, paused, or archived, as appropriate to existing conventions.
- Business purpose or audience description.
- Owner and responsible team, where supported.
- Criteria definition and criteria version.
- Included and excluded audience rules.
- Membership count and last evaluation time.
- Evaluation status and last evaluation error, where appropriate.
- Created by, updated by, and timestamps.
- Tenant or organization association, following existing data isolation patterns.
- Optional labels or categories, using existing tagging or metadata capabilities where available.

Enforce uniqueness within the correct tenant or organizational scope.

Prevent unauthorized users from viewing, editing, evaluating, or archiving segments belonging to another tenant or restricted organizational scope.

Provide clear empty, loading, success, and error states in the UI.

## 5. Dynamic Segments

A dynamic segment defines its audience through saved, validated rules evaluated against authoritative business data.

Examples of general-purpose criteria include:

- Contact or customer status.
- Lead status or qualification state.
- Customer type or classification, if present in the existing schema.
- Location or region, if available and authorized.
- Account ownership or assigned sales representative.
- Creation date or last activity date.
- Existing CRM engagement or interaction information.
- Existing tags, categories, or custom fields.
- Existing purchase or transaction history, but only where reliable, authorized data is already available.
- Existing communication preferences or eligibility attributes.
- Combinations of supported attributes.

These are examples, not a mandate to create new CRM fields. Only expose fields that actually exist, are supported by the data-source integration, and are authorized for use.

### Rule behavior

Support:

- Multiple criteria combined with AND and OR.
- Grouped conditions, where feasible within the existing architecture.
- Nested groups only if they can be implemented safely and tested reliably.
- Operators appropriate to each field type, such as equals, not equals, in list, contains, starts with, greater than, less than, between, is empty, and is not empty.
- Date and date-range conditions.
- Numeric comparisons.
- Boolean comparisons.
- Null and missing-value handling.
- Explicit handling of inactive, archived, and deleted records.
- Reusable saved criteria that can be edited and evaluated again.

Validate all criteria on the server, even if the UI already validates them.

Clearly define how null values, empty values, time zones, date boundaries, and case sensitivity behave. Use consistent semantics throughout the application.

### Security requirements for the criteria engine

Do not execute user-supplied SQL, scripts, expressions, or arbitrary code.

Use a safe query builder, allowlisted fields and operators, parameterized queries, and server-side validation.

Prevent:

- SQL injection.
- Unauthorized access to sensitive fields.
- Cross-tenant data leakage.
- Unsupported relationship traversal.
- Unbounded queries that can overload the database.
- Exposure of internal database structure through errors.
- Access to data that the requesting user is not authorized to view.

Apply tenant and authorization constraints to every query, preview, count, export, and membership evaluation.

## 6. Static Segments

Support static segments whose membership is explicitly maintained rather than automatically determined by current criteria.

Depending on the existing application architecture, support:

- Adding an existing eligible CRM record to a segment.
- Removing a record from a segment.
- Adding or removing multiple selected records through a bounded, validated operation.
- Viewing the membership list.
- Recording who added or removed a member and when.
- Recording the source or reason for a membership change where appropriate.
- Preventing duplicate memberships.
- Preserving a history of membership changes through existing audit mechanisms.

Static membership must reference existing CRM records using their canonical identifiers. Do not create duplicate customer, account, lead, or contact records.

If bulk membership import is not supported safely by existing infrastructure, defer file import rather than introducing a separate import framework in this phase.

### Static membership semantics

A static segment represents an explicitly maintained membership list, not a continuously recalculated criteria result.

Define whether eligibility checks are performed when adding members, when previewing the segment, and when preparing an audience for downstream use. Do not silently delete or rewrite historical membership because a contact later becomes inactive or ineligible.

## 7. Audience Criteria Builder UI

Create a usable interface for defining and managing segment rules.

The criteria builder should:

1. Display only fields supported by the selected data source.
2. Present field-appropriate operators.
3. Render suitable value controls for text, numbers, dates, booleans, and enumerated values.
4. Support adding, editing, and removing conditions.
5. Support AND/OR grouping within the implemented complexity limits.
6. Validate incomplete or contradictory rules.
7. Clearly identify unsupported or unavailable fields.
8. Allow the user to save a draft without prematurely activating it.
9. Allow authorized users to preview the matching audience before activation.
10. Explain validation errors in understandable language.

The backend must remain authoritative. Never trust client-supplied field names, operators, record identifiers, or eligibility results.

Use existing design-system components, routing, forms, data tables, permissions, and API patterns.

Avoid building a generic visual programming environment. The UI should be focused, understandable, and maintainable.

## 8. Audience Preview and Membership Counts

Provide a preview of the records matching a segment.

Where permitted, display useful fields such as:

- Name or display name.
- Record type.
- Organization or account association.
- Relevant classification.
- Current status.
- Owner.
- Eligibility status, when supported by authoritative data.

Respect existing privacy controls and field-level permissions. Do not expose sensitive fields merely because they are available in the database.

Support:

- Total matching count.
- A paginated sample of matching records.
- Included and excluded counts where available.
- Counts of records omitted because they are inactive or ineligible, if the relevant information exists.
- Last evaluated time.
- Evaluation status and meaningful validation errors.

Clearly distinguish an estimated or live preview count from a persisted membership snapshot.

Preview operations must not create external side effects or send communications.

Use pagination and appropriate query limits. Avoid loading the entire matching audience into application memory.

If a query is too expensive, provide a controlled failure or asynchronous evaluation path instead of allowing unbounded processing.

## 9. Segment Evaluation and Membership Calculation

Create a reliable server-side segment evaluation service.

For dynamic segments, it must:

1. Load the saved, authorized segment definition.
2. Validate the definition and its version.
3. Resolve the configured data sources and supported fields.
4. Apply tenant and access constraints.
5. Evaluate the criteria using safe queries.
6. Apply supported exclusions and eligibility rules.
7. Deduplicate membership by the canonical record identifier and record type.
8. Persist evaluation status, counts, and timestamps.
9. Record the segment definition version used for evaluation.
10. Report failures without silently presenting stale results as current.

Use asynchronous processing and existing background-job infrastructure when evaluation size or duration warrants it.

Implement appropriate limits, batching, retry behavior, and protection against concurrent evaluations.

Prevent older or slower evaluations from overwriting the results of newer segment versions. Use version checks, evaluation identifiers, or equivalent concurrency controls.

### Membership provenance

For each persisted membership or snapshot entry, preserve enough information to determine, where supported:

- Which segment and segment version produced it.
- Which source record it references.
- When membership was evaluated or added.
- Whether membership came from dynamic evaluation or explicit static membership.
- Which evaluation or operation created the entry.
- Whether the record was excluded or ineligible at the time, if that outcome is retained.

Do not duplicate entire CRM records inside the segment tables. Store canonical references and only the minimum additional information required for membership history and reproducibility.

## 10. Segment Versioning and Membership Snapshots

Implement versioning that protects the integrity of audience definitions and downstream campaign use.

At minimum:

- Track meaningful changes to criteria and exclusions.
- Associate each evaluation with the segment-definition version used.
- Distinguish the current segment definition from previously evaluated results.
- Record evaluation timestamps and outcome counts.
- Prevent a modified definition from being confused with a snapshot produced by an earlier definition.
- Preserve the history needed to investigate why a record was included or excluded.

Where a campaign needs a reproducible audience, provide a way to reference a specific segment version and membership snapshot.

A snapshot must represent a consistent set of canonical record references captured at a known point in time. Use transactions, version checks, or another reliable approach to prevent partially written snapshots from appearing complete.

If a snapshot fails, mark it as failed or incomplete and make sure it cannot be mistaken for a valid completed snapshot.

Define and document the retention approach using existing data-retention policies. Do not retain personal data indefinitely without an established business or legal basis.

### Critical distinction

- **Dynamic segment:** Membership can change as source data changes or the segment is reevaluated.
- **Static segment:** Membership changes through explicit, auditable operations.
- **Membership snapshot:** A recorded audience state tied to a particular segment version and evaluation time.

Do not conflate these three concepts.

## 11. Exclusions, Deduplication, and Eligibility

Allow segments to exclude records based on supported rules or references to existing authoritative exclusion mechanisms.

Where supported, account for:

- Explicitly excluded records.
- Inactive, deleted, or archived CRM records.
- Existing unsubscribe or opt-out status.
- Existing communication preferences and consent records.
- Existing suppression lists.
- Invalid or unavailable contact information where relevant to downstream channel eligibility.
- Records that the requesting user is not authorized to use.

Apply exclusions consistently in previews, evaluations, and persisted snapshots.

Deduplicate by canonical record identity. Do not treat two different contacts as the same merely because their names match.

Do not silently merge different CRM entities or infer identity from weak matching criteria.

### Consent and privacy are mandatory safeguards

Reuse the existing consent, preference, and suppression systems if they exist.

If authoritative consent or opt-out data is unavailable:

- Do not invent consent fields or fabricate a compliant status.
- Do not assume that a record has consented.
- Clearly indicate that consent eligibility cannot be verified.
- Provide a documented integration interface or eligibility result that downstream marketing execution can require.
- Do not describe an audience as ready to receive marketing communications unless the necessary eligibility checks have actually been verified.

Audience membership alone must never imply permission to contact a person.

Segment evaluation must not override existing opt-outs or other authoritative restrictions.

## 12. Integration with Phase 08 Campaign Management

Integrate segments with the existing Marketing Campaign Management functionality.

Support applicable capabilities such as:

- Selecting an existing segment for a campaign.
- Viewing the segment definition, status, version, and last evaluation.
- Previewing its current audience count.
- Referencing a particular membership snapshot when reproducibility is required.
- Showing when the current segment definition differs from the snapshot associated with the campaign.
- Validating that a selected segment exists and is accessible to the user.
- Preventing references to archived, inaccessible, or otherwise invalid segments according to the agreed business rules.

Reuse the campaign records and relationships established in Phase 08.

Do not create a second campaign module or duplicate campaign lifecycle, ownership, approval, or audit functionality.

A campaign may need multiple segments or exclusion segments. Support this only if it fits the existing data model and can be implemented without compromising clear audience semantics. If supported, define how inclusion, exclusion, and deduplication interact.

**Selecting a segment or producing a snapshot must not send a message, launch an advertisement, publish content, or trigger any external campaign execution.**

Those capabilities belong to Phase 10 and later phases.

Potential entities, depending on the repository's current design, may include:

- Audience segment.
- Versioned segment definition or criteria.
- Segment evaluation run.
- Segment membership.
- Membership snapshot.
- Snapshot membership entries.
- Segment exclusion references, if needed.
- Campaign-to-segment or campaign-to-snapshot association.

These are conceptual possibilities, not instructions to create every table.

Before adding a new entity, verify that an equivalent reusable structure does not already exist.

Requirements:

- Use canonical references to existing CRM entities.
- Enforce tenant isolation at the data-access layer.
- Add appropriate indexes for frequently used filters, membership lookups, and status queries.
- Prevent duplicate memberships with appropriate uniqueness constraints.
- Use foreign keys or equivalent referential-integrity mechanisms where compatible with the architecture.
- Handle source records that are deleted, archived, merged, or otherwise unavailable.
- Ensure migrations are reversible where supported by project conventions.
- Avoid unnecessary denormalization and duplication of personal data.

Document important design decisions, especially snapshot retention, segment versioning, and the handling of deleted source records.

## 16. Performance, Reliability, and Operational Safety

The implementation must be suitable for a growing ERP deployment.

Address:

- Indexed lookups and paginated results.
- Efficient criteria evaluation.
- Bounded query complexity.
- Batch processing for large audiences.
- Configurable evaluation limits where appropriate.
- Background jobs for expensive calculations.
- Job status, error handling, and retry behavior.
- Concurrent evaluation protection.
- Snapshot consistency.
- Idempotent membership updates.
- Stale-result detection.
- Structured logging and operational observability.
- Graceful handling of unavailable source data.

Do not introduce an in-memory full-table scan as the default evaluation strategy.

Do not automatically refresh every segment after every source-data change unless existing infrastructure and the repository's scale justify it. Prefer a controlled refresh mechanism that can later be extended with event-driven invalidation or scheduled recalculation.

If a feature cannot be implemented safely within the existing infrastructure, document the limitation instead of presenting a fragile workaround as production-ready.
