# Phase 02: Sales Enquiries and Quotation Management

## 1. Your Role

Act as a senior ERP software architect, full-stack developer, database engineer, and QA engineer.

You are working on a comprehensive, modular, multi-industry ERP system. Your task is to implement **Phase 02: Sales Enquiries and Quotation Management** within the existing codebase.

This is a production-oriented ERP module intended to support different industries, business models, sales channels, products, services, and commercial workflows. Do not hardcode assumptions for any single industry.

You must inspect the existing repository, understand the architecture, and implement this phase using the established technology stack, coding conventions, UI patterns, APIs, security model, database conventions, and testing framework.

Do not create a separate application or introduce a parallel architecture.

## 2. Mandatory Pre-Implementation Inspection

Before changing code, inspect:

1. The Phase 01 implementation and its completion report.
2. The Sales & Marketing Feature Requirements Document.
3. The project's architecture and development documentation.
4. Existing frontend routes, navigation, page layouts, shared components, forms, tables, dialogs, and notification patterns.
5. Existing backend modules, API conventions, service layers, validation, error handling, and database models.
6. Existing authentication, organization/tenant isolation, authorization, and permission checks.
7. Existing CRM entities and workflows, including leads, contacts, accounts, opportunities, activities, and customer records.
8. Existing product and service catalogs, units of measure, currencies, taxes, pricing, and customer master data.
9. Existing quotation, estimate, proposal, order, or sales-document functionality anywhere in the repository.
10. Existing document numbering, approval workflows, audit logs, event publishing, file attachments, and background jobs.
11. Existing automated tests and development commands.

Search the entire repository for existing functionality before creating new models, tables, endpoints, screens, or services.

### Architecture reuse rules

- Reuse existing CRM entities and relationships. Do not recreate leads, contacts, accounts, customers, or opportunities.
- Reuse existing product and service catalogs, units of measure, currency handling, tax configuration, and pricing infrastructure wherever appropriate.
- Reuse existing document numbering and approval mechanisms if available.
- Reuse existing sales order functionality. A quotation accepted by a customer must integrate with the existing order workflow rather than create a duplicate order system.
- Reuse existing authentication, authorization, tenant isolation, audit logging, and event infrastructure.
- Do not create duplicate master data or generic infrastructure that already exists.
- If equivalent functionality already exists, extend it safely rather than building a parallel implementation.
- If a required dependency does not exist, implement only the smallest reusable component necessary for this phase.
- If architectural uncertainty materially affects data integrity or integration, document the issue and seek clarification before making an irreversible design decision.

## 3. Phase Objective

Build a complete Sales Enquiries and Quotation Management workflow that allows authorized users to:

1. Receive and record sales enquiries.
2. Associate enquiries with existing CRM records.
3. Qualify and manage enquiries.
4. Assign ownership and follow-up responsibilities.
5. Track enquiry progress and outcomes.
6. Convert eligible enquiries into quotations.
7. Create, calculate, revise, review, approve, issue, and manage quotations.
8. Generate customer-facing quotation documents.
9. Track quotation delivery, validity, acceptance, rejection, and expiry.
10. Revise quotations while preserving version history.
11. Record customer feedback and commercial negotiation history.
12. Convert an accepted quotation into an existing Sales Order through the established workflow.
13. View enquiry and quotation activity, status, performance, and history.
14. Enforce permissions, validation, auditability, and organization-level data isolation.

The result must be a usable end-to-end workflow, not merely a set of database tables or static screens.

## 5. Functional Requirements

### 5.1 Sales Enquiry Management

Create a searchable and filterable Sales Enquiries workspace.

Each enquiry should support the following fields where appropriate to the existing architecture:

- Unique enquiry reference.
- Enquiry subject or title.
- Enquiry description and requirements.
- Enquiry source or channel.
- Enquiry received date and time.
- Related CRM lead, opportunity, account, contact, or customer.
- Requesting person's details when no existing CRM contact is available, without creating a duplicate CRM record automatically.
- Assigned sales representative or owner.
- Team or business unit, if supported.
- Priority.
- Enquiry status.
- Expected response date or follow-up date.
- Requested products or services.
- Requested quantities and units, where applicable.
- Requested delivery or service date, where applicable.
- Customer-provided budget or target price, if supplied.
- Currency, if applicable.
- Attachments or supporting documents through the existing file-management system.
- Internal notes.
- Created by, created at, updated by, and updated at.
- Related quotation references.
- Closure reason and outcome where applicable.

Use configurable or extensible source and status values when the existing architecture supports configuration. Avoid hardcoded industry-specific enquiry categories.

Do not store sensitive or unnecessary personal information.

### 5.2 Enquiry Lifecycle

Support a coherent lifecycle using the project's established workflow patterns.

A reasonable default lifecycle is:

- New
- Under Review
- Qualified
- Quotation in Progress
- Quotation Issued
- Converted
- On Hold
- Closed - Won
- Closed - Lost
- Closed - Not Qualified

Adapt these statuses if the existing CRM or workflow engine already defines an appropriate lifecycle. Do not create conflicting status systems.

Implement valid state transitions and prevent invalid operations.

Examples:

- A new enquiry can be reviewed, assigned, qualified, or marked not qualified.
- A qualified enquiry can initiate a quotation.
- An enquiry with an issued quotation can be linked to quotation updates.
- An enquiry can be closed as won or lost with an appropriate outcome.
- Reopening a closed enquiry must follow an explicit, auditable rule.
- An enquiry must not be marked converted unless the relevant conversion has succeeded.

Do not rely on the frontend alone to enforce transitions. Validate them on the backend.

### 5.3 Enquiry Assignment and Follow-up

Provide functionality to:

- Assign or reassign an enquiry to an authorized user.
- Set priority and follow-up date.
- Record internal notes and customer interactions.
- Display overdue follow-ups.
- Display the assigned owner and current status.
- Maintain a chronological activity history.
- Trigger notifications through existing infrastructure where supported.

Do not duplicate the CRM activity timeline. Link to or reuse it where suitable. If no suitable activity mechanism exists, add only the minimum reusable enquiry activity capability needed for this workflow.

### 5.4 Enquiry Qualification

## 6. Quotation Management

### 6.1 Quotation Creation

Allow authorized users to create quotations from eligible enquiries and, if consistent with existing CRM workflows, from appropriate existing CRM records.

Support standalone quotations only if the business architecture permits them. Do not require an enquiry for every quotation if the ERP needs to support direct quotation requests.

A quotation should include, where applicable:

- Unique quotation number.
- Quotation title or subject.
- Linked enquiry.
- Linked CRM account, customer, contact, or opportunity.
- Issue date.
- Valid-until date.
- Quotation currency.
- Relevant exchange-rate reference if the existing currency system supports it.
- Bill-to and ship-to or service-location references, if applicable.
- Customer-facing introduction or description.
- Quotation line items.
- Commercial terms.
- Payment terms reference, if supported.
- Delivery or service terms.
- Tax configuration and calculated tax values.
- Discounts, using existing supported discount capabilities.
- Freight, fees, or other charges where applicable.
- Subtotal.
- Discount total.
- Tax total.
- Other charges.
- Grand total.
- Internal notes.
- Customer-facing notes.
- Terms and conditions.
- Attachments.
- Created by, created at, updated by, and updated at.

Use existing shared customer, address, currency, tax, and commercial-term structures whenever available.

### 6.2 Quotation Line Items

Support multiple quotation lines.

Each line should support appropriate fields such as:

- Product or service reference.
- Line description.
- Quantity.
- Unit of measure.
- Unit price.
- Discount information, where supported.
- Tax category or tax treatment, where applicable.
- Line subtotal.
- Tax amount.
- Line total.
- Optional requested delivery date or service details.
- Optional customer reference or specification.

Allow manually described non-catalog items only if consistent with existing product governance and the ERP's business rules. Such items must not silently create permanent product master records.

Use the existing product and service catalog rather than maintaining duplicated product information.

### 6.3 Calculation Engine

Implement reliable, server-side quotation calculations.

Requirements:

- Validate quantities, prices, discounts, and applicable taxes.
- Use appropriate decimal arithmetic and currency precision.
- Define and consistently apply rounding rules.
- Prevent clients from submitting trusted grand totals without server verification.
- Recalculate totals when relevant line values or commercial inputs change.
- Ensure line totals, subtotals, discounts, taxes, fees, and grand totals reconcile.
- Apply only tax and discount functionality that is already supported or necessary for this phase.
- Do not introduce a competing tax engine or implement the full Phase 03 pricing engine.
- Preserve the calculation inputs and applicable configuration needed to understand previously issued quotations.
- Clearly handle zero-priced lines, permitted negative adjustments, zero quantities, and invalid values according to business rules.

Document the calculation order and rounding rules in code or technical documentation.

All persisted totals must be calculated or verified by the backend.

### 6.4 Quotation Lifecycle

Support a controlled quotation lifecycle. Adapt it to any existing workflow engine or established document statuses.

A reasonable default lifecycle is:

- Draft
- Pending Review
- Pending Approval
- Approved
- Issued
- Viewed, if reliable delivery or document-view tracking exists
- Accepted
- Rejected
- Expired
- Superseded
- Cancelled

Do not imply that a customer has viewed a quotation unless the system has reliable evidence.

Rules:

- Draft quotations can be edited by authorized users.
- Submission for review or approval must trigger the existing workflow where available.
- Only authorized users may approve quotations when approval is required.
- Issued quotations must not be silently overwritten.
- Material changes to an issued quotation must create a new revision.
- Acceptance must reference the exact quotation revision being accepted.
- Expiry must respect the validity date and business timezone rules.
- Rejected, cancelled, or superseded quotations must not be accepted without an explicit permitted recovery workflow.
- Duplicate conversion into a Sales Order must be prevented.
- All meaningful lifecycle transitions must be validated server-side and recorded in the audit history.

Do not force approval for every quotation if the ERP supports configurable approval thresholds. If approval configuration does not yet exist, use the smallest secure and configurable mechanism appropriate to the existing architecture; document any temporary limitation.

### 6.5 Quotation Revision and Version History

Implement versioning so that commercial changes remain traceable.

Requirements:

- Maintain a stable quotation identity and identifiable revisions.
- Preserve previously issued quotation content.
- Record revision number, revision date, revision creator, and revision reason.
- Maintain a snapshot of the commercial details associated with each issued revision.
- Track which revision was sent, accepted, rejected, superseded, or converted.
- Link replacement revisions to their predecessors.
- Prevent changes to historical issued revisions except through explicitly supported administrative correction mechanisms.
- Record changes to important commercial fields in the audit trail.
- Ensure the customer-facing document generated for an issued revision can be reproduced or reliably reconstructed.

Do not implement versioning as a simple revision-number field while overwriting historical values.

### 6.6 Review and Approval

Integrate with the existing workflow and approval infrastructure.

Where supported, enable configurable review or approval based on business rules such as:

- Quotation total.
- Discount level.
- Margin-related criteria, if the system already supports reliable margin calculations.
- Currency.
- Business unit.
- Customer classification.
- Other existing configurable criteria.

If no approval engine exists, implement a minimal, reusable approval integration without creating a duplicate workflow platform.

Requirements:

- Record approval requests and outcomes.
- Identify the approver and timestamp.
- Record comments or reasons when required.
- Prevent unauthorized self-approval when the configured policy prohibits it.
- Prevent issue or sending before mandatory approval.
- Handle rejection and resubmission appropriately.
- Ensure approvals apply to the correct quotation revision.

Never assume approval requirements based on a specific industry.

### 6.7 Quotation Documents

Generate a professional customer-facing quotation using the existing document generation, PDF, or template infrastructure.

The document should support:

- Company identity and branding from existing organization settings.
- Quotation number and revision.
- Issue and expiry dates.
- Customer and relevant address details.
- Itemized products or services.

- Subtotal and final amount.
- Currency.
- Terms and conditions.

- Ensure generated documents match the correct quotation revision.
- Handle missing optional data gracefully.
- Provide preview and download actions where supported.

### 6.8 Sending and Communication Tracking

Integrate with existing email, notification, messaging, or document-delivery infrastructure.

Support, where available:

- Sending a quotation to an authorized customer contact.
- Selecting from eligible existing contact records.
- A configurable message or email template.
- Attaching or linking the generated quotation document.
- Recording send attempts, timestamps, recipients, and delivery outcomes when provided by the provider.
- Retrying transient failures safely.
- Showing the latest communication status.
- Recording the user who initiated the send.

Do not invent delivery success when only a send request was submitted.

If external messaging providers are not configured, provide a clear integration boundary and usable document download workflow. Do not hardcode credentials or claim that messages were sent.

Avoid duplicating the dedicated Marketing Channels functionality planned for a later phase.

### 6.9 Customer Acceptance and Rejection

Support authorized recording of customer acceptance or rejection.

Acceptance should capture, as applicable:

- Accepted quotation and revision.
- Acceptance date and time.
- Acceptance method.
- Authorized user recording the acceptance.
- Customer reference or supporting evidence.
- Optional acceptance comments.
- Audit information.

Rejection should capture a reason where appropriate.

If the platform already supports secure customer portals or electronic acceptance, integrate with those mechanisms. Do not create a publicly accessible acceptance endpoint without appropriate security, identity verification, authorization, and audit controls.

Do not represent a quotation as customer-accepted merely because an internal user approved it.

### 6.10 Quotation Expiry

Implement reliable expiry behavior.

Requirements:

- Determine expiry using the validity date and the organization's timezone rules.
- Prevent an expired quotation from being newly accepted unless an authorized extension or reopening workflow permits it.
- Record expiry transitions in a reliable way.
- Use existing scheduled jobs or background processing where available.
- If scheduled processing is not available, ensure expiry is derived consistently when the quotation is accessed or acted upon, and document any operational limitations.
- Do not create unnecessary background workers or a new scheduling framework.

### 6.11 Conversion to Sales Order

Integrate accepted quotations with the existing Sales Order Management module.

Requirements:

- Convert only an eligible, accepted quotation revision.
- Use the existing order creation service, API, or workflow.
- Pass the appropriate customer, currency, lines, quantities, prices, taxes, discounts, terms, and references supported by the existing order model.
- Preserve links between the originating enquiry, quotation, accepted revision, and created order.
- Record conversion status and timestamp.
- Prevent duplicate order creation under retries or concurrent requests.
- Use transactions or idempotency mechanisms appropriate to the existing architecture.
- Validate all order prerequisites before conversion.
- Handle failures without leaving misleading partial states.
- Respect existing order validation, authorization, and approval requirements.

If the Sales Order module is not yet available, do not create a duplicate order-management module. Implement a clearly defined integration interface and document the missing dependency. Only implement a minimal adapter if it fits the established architecture.

## 15. Acceptance Criteria

1. An authorized user can create, search, view, assign, qualify, update, and close a sales enquiry.
2. An enquiry can link to existing CRM records without duplicating them.
3. An eligible enquiry can initiate a quotation.

5. The backend validates quotation data and calculates monetary totals reliably.
6. Quotations follow valid lifecycle transitions.
7. Required approval rules are enforced through the existing workflow or the documented minimal implementation.
