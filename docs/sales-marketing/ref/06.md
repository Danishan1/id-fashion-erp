Build a comprehensive Sales Forecasting and Analytics capability that enables authorized users to:

- Forecast future sales using configured methods and reliable source data.
- Evaluate forecast performance against approved sales targets.
- Analyze the sales pipeline and expected future outcomes.
- Understand historical trends, growth, conversion, and performance patterns.
- Compare forecasts with actual results over consistent periods.
- Identify risks, gaps, and significant changes in forecast assumptions.

Forecasts must be explainable, reproducible, auditable, and clearly distinguished from actual business results.

The implementation must not silently represent forecasts as confirmed orders, invoiced sales, recognized revenue, or collected cash.

## 4. Forecasting Concepts and Terminology

Use consistent terminology throughout the system.

### Actuals

Actuals are historical values calculated from authoritative source records under explicitly defined metric rules.

Examples include booked Sales Order value, invoiced sales value, or collected payment value, provided the corresponding source module supports reliable calculations.

Reuse Phase 05 metric definitions wherever possible.

### Pipeline

Pipeline represents eligible, not-yet-completed sales activity from existing CRM, enquiry, quotation, or opportunity records.

Pipeline is not automatically equivalent to expected revenue. Its meaning depends on record eligibility, stage, value, probability, expected close date, and the selected forecasting method.

### Forecast

A forecast is an estimate of future outcomes based on an identified method, source data, assumptions, and time horizon.

### Target

A target is an approved business goal managed through Phase 05.

A forecast does not replace or automatically modify a target.

### Scenario

A scenario is a controlled set of assumptions used to evaluate alternative possible outcomes without changing authoritative operational records.

### Forecast snapshot

A forecast snapshot preserves the forecast as it was calculated at a particular point in time, including its method, inputs, assumptions, and relevant configuration.

Use these distinctions consistently in database models, APIs, dashboards, reports, and documentation.

## 7. Forecasting Methods

Implement a modular forecasting service with explicit method definitions and consistent input/output contracts.

Do not build one large service containing all forecasting logic.

At minimum, evaluate the following methods and implement those supported reliably by the repository and available data.

### 7.1 Pipeline-weighted forecast

Calculate expected outcomes from eligible open pipeline records using their values, probabilities, and expected close dates.

A basic calculation may be:

Weighted pipeline value = eligible pipeline value × applicable probability.

For individual records:

Weighted value = eligible record value × applicable probability.

Define how the calculation handles:

- Missing probabilities.
- Missing or invalid expected close dates.
- Closed, cancelled, lost, expired, or otherwise ineligible records.
- Records already converted into Sales Orders.
- Records that have been superseded by a newer quotation revision.
- Duplicate records representing the same commercial opportunity.
- Missing or stale values.
- Records with different currencies.
- Probability values outside the permitted range.

Use the existing CRM stage and probability configuration where available.

Do not hardcode industry-specific stage names or probability values.

If probability defaults are necessary, make them configurable and disclose that they are defaults rather than empirically validated predictions.

Avoid counting both a quotation and its resulting Sales Order as independent future pipeline value.

### 7.2 Historical trend-based forecast

Where sufficient historical data exists, implement one or more transparent methods, such as:

- Moving average.
- Weighted moving average.
- Period-over-period trend.
- Simple growth-rate projection.
- Seasonal comparison, only when sufficient history supports it.

Each method must define:

- Minimum historical data requirements.
- Historical lookback period.
- Missing-period behavior.
- Treatment of zero and negative values.
- Treatment of outliers, if applicable.
- Calculation frequency.
- Forecast horizon.
- Rounding and precision.
- Known limitations.

Do not apply a growth rate or seasonal pattern automatically when the available data does not justify it.

If there is insufficient history, return a clear data-insufficiency result rather than fabricating a forecast.

### 7.3 Target-informed analysis

Compare existing Phase 05 targets with forecasts and actuals.

Calculate, where applicable:

- Target value.
- Actual value to date.
- Forecasted period total.
- Forecast-to-target gap.
- Forecast attainment percentage.
- Remaining amount required to achieve the target.
- Historical target attainment.

Do not use the target itself as if it were historical evidence of expected sales.

Keep target, actual, and forecast fields distinct.

### 7.4 Forecast method extensibility

Define an appropriate interface or strategy abstraction so additional forecasting methods can be introduced later without rewriting the dashboard, API, or persistence layer.

Do not introduce a machine-learning platform, external forecasting service, or complex mathematical dependency without a clear business need and repository support.

Document which methods are implemented and which remain unavailable.

## 8. Pipeline Eligibility and Probability Rules

Pipeline forecasting depends on reliable pipeline data.

Use the existing CRM and quotation lifecycle as the source of truth.

### Requirements

Define eligibility based on actual repository statuses and documented business rules.

For example, closed-won records may be represented by the corresponding Sales Order or another authoritative completed state, while closed-lost, cancelled, expired, or superseded records should generally not contribute to open pipeline forecasts.

Do not assume the ERP uses any particular CRM stage naming convention.

Where both opportunity-level and quotation-level records exist, define which entity represents the pipeline unit and prevent duplication.

Use expected close dates to assign pipeline values to forecast periods.

If a record has no valid expected close date, handle it according to an explicit configuration or exclusion policy and report its exclusion. Do not silently place it in an arbitrary period.

Where probabilities are derived from CRM stages, reuse existing configuration. If no stage-probability configuration exists, implement a minimal configurable mapping only if required.

Validate probability ranges, such as zero to one or zero to one hundred, according to the existing system convention. Normalize values consistently.

Show the method and probability assumptions used to produce each pipeline forecast.

## 10. Forecast Accuracy and Backtesting

Implement forecast accuracy analysis using historical forecast snapshots and subsequently observed actuals.

### 10.1 Forecast snapshots

Persist enough information to reproduce and evaluate historical forecasts, including:

- Forecast configuration and version.
- Forecast method and parameters.
- Forecast generation timestamp.
- Forecast scope and period.
- Input data cutoff or snapshot reference.
- Relevant probabilities and assumptions.
- Predicted values.
- Currency and unit.
- Data quality or limitation indicators.

Follow existing storage patterns and avoid duplicating full source records unnecessarily.

A forecast regenerated today must not overwrite the historical forecast used to evaluate a prior prediction.

### 10.2 Accuracy metrics

Where appropriate for the selected metric and data characteristics, calculate:

- Absolute error.
- Percentage error, where the actual denominator is valid.
- Mean absolute error.
- Mean absolute percentage error, only when mathematically meaningful.
- Weighted absolute percentage error, where appropriate.
- Forecast bias.
- Forecast-versus-actual variance.

Document formulas and edge-case behavior.

Percentage-based metrics require careful handling of zero or near-zero actuals. Do not produce misleading percentages by dividing by zero or hiding excluded periods.

Where a metric is inappropriate for the data, report it as unavailable with an explanation.

### 10.3 Backtesting

Where sufficient historical data and snapshot history are available, provide a repeatable way to evaluate forecast methods against historical outcomes.

Avoid data leakage: historical forecasts must use only information that would have been available at the forecast creation time.

If historical snapshots do not exist, do not invent past forecasts. Explain that meaningful historical forecast-accuracy analysis will become available after snapshots accumulate.

### 10.4 Method comparisons

Where supported, compare methods using the same scope, periods, actual definitions, and data cutoffs.

Do not declare one method superior based on incomparable datasets.

Provide sufficient context for users to understand the result.

## 11. Scenario Planning and Sensitivity Analysis

- Pipeline conversion probability.
- Expected close timing.
- Sales growth rate.
- Selected pipeline inclusion criteria.
- Other method-specific parameters.

Only expose parameters that the selected method actually uses.

For each scenario, display:

- Baseline forecast.
- Scenario forecast.
- Absolute difference.
- Percentage difference where meaningful.
- Adjusted assumptions.
- Forecast horizon.
- A clear indication that the result is hypothetical.

Support saving, comparing, and revisiting scenarios where appropriate.

### Scenario safeguards

- Scenario changes must not alter authoritative CRM records.
- Scenario changes must not alter Sales Orders, quotations, pricing, targets, invoices, or payments.
- Do not silently change the baseline forecast.
- Record who created or modified a saved scenario.
- Preserve scenario assumptions and results for reproducibility.
- Enforce permissions and tenant boundaries.

Do not implement complex financial simulations or unrestricted arbitrary formulas unless supported by the existing architecture and explicitly required by the business requirements.

## 17. Performance, Reliability, and Operational Behavior

Design for increasing transaction volume.

- Avoid N+1 queries.
- Use efficient aggregation queries.
- Bound expensive historical lookbacks.
- Avoid loading all source records into application memory.
- Reuse shared metric calculations.
- Cache results only when invalidation and freshness rules are clear.
- Use background processing for genuinely expensive calculations.
- Prevent duplicate processing.
- Support safe retry and failure recovery.
- Record calculation status and timestamps.
- Make stale results visible.
- Provide a reconciliation path for stored results.
- Avoid running heavy forecast calculations on every dashboard request.

Keep the architecture simple enough to maintain. Do not add external infrastructure unless the repository and workload justify it.
