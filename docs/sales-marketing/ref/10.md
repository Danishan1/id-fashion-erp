# Phase 10: Marketing Channels and Provider Integrations

## 1. Objective

Implement a production-oriented **Marketing Channels and Provider Integrations** capability within the existing Sales & Marketing ERP module.

The objective is to enable authorized users to configure supported marketing channels, connect external providers, prepare and execute campaign deliveries, monitor execution, handle provider responses, and manage delivery failures through a consistent integration architecture.

The solution must be industry-agnostic and reusable across different business types, industries, markets, and organizational structures.

Build a provider-independent architecture that supports multiple external providers for a channel without coupling campaign management to any single vendor.

This phase must integrate with the existing:

- Sales & Marketing foundation from Phase 01.
- Enquiries and quotations from Phase 02.
- Pricing functionality from Phase 03.
- Sales order integration from Phase 04.
- Sales targets and team performance from Phase 05.
- Sales forecasting and analytics from Phase 06.
- Sales channels, commissions, and incentives from Phase 07.
- Marketing campaigns from Phase 08.
- Audience segments, evaluations, and snapshots from Phase 09.

Do not recreate these modules. Extend them through their established interfaces.

**Critical principle:** a campaign, segment, or delivery request is not proof that an external provider accepted, sent, delivered, or displayed the content. Track each stage separately using authoritative application and provider responses.

Before modifying code:

1. Inspect the repository architecture, coding standards, project documentation, existing tests, and deployment conventions.
2. Review the Sales & Marketing Feature Requirements Document and all implemented work from Phases 01–09.
3. Identify existing implementations for:
   - Campaign management and lifecycle transitions.
   - Segment definitions, membership evaluation, exclusions, and snapshots.
   - CRM contacts and customer records.
   - Consent, communication preferences, unsubscribe records, and suppression lists.
   - Authentication, authorization, tenant isolation, and secret management.
   - Background jobs, schedulers, queues, retries, and distributed locking.

   - Email, SMS, messaging, advertising, or other provider integrations.
   - File storage and existing asset handling.
   - API conventions, webhooks, rate limiting, and request validation.
   - Notification and delivery tracking systems.
4. Determine which integration mechanisms and provider adapters already exist.
5. Reuse existing infrastructure wherever appropriate.

Do not assume that a provider, feature, field, consent record, or API exists without verifying it.

If a required dependency is absent, document the gap and create a clean abstraction or integration boundary where appropriate. Do not fabricate provider capabilities or claim that an integration is operational without testing it.

Implement the shared infrastructure for marketing channel delivery, including:

5. Audience preparation using Phase 09 segments and snapshots.

Prioritize a maintainable provider-independent framework and a small number of complete, real integrations appropriate to the repository and available credentials.

Do not build superficial integrations that only simulate success.

## 4. Channel Registry and Configuration

Implement a consistent model for supported marketing channels.

Potential channel types include:

- Email.
- SMS.
- Business messaging services, such as WhatsApp, where a supported provider and required business configuration are available.
- Advertising platforms.
- Website or landing-page distribution integrations.
- Other approved marketing delivery channels supported by the architecture.

These are examples, not a requirement to implement every channel or every provider in this phase.

Represent channels using a controlled, extensible registry rather than hard-coded logic spread throughout campaign screens and business services.

Each configured channel should support appropriate fields such as:

- Channel type.
- Display name.
- Internal identifier.
- Description.
- Provider reference.
- Configuration status.
- Active or disabled status.
- Default sender identity or account reference, where applicable.
- Supported capabilities.
- Supported message or campaign types.
- Rate-limit settings, where applicable.
- Last connection or health-check status, where supported.
- Created and updated timestamps.
- Tenant or organization ownership.

Separate the conceptual channel from the provider implementation. For example, an email channel should not be permanently tied to one email vendor.

Validate that each provider supports the requested channel, content format, sender identity, and operation before allowing execution.

Reuse existing configuration patterns and avoid creating a second general-purpose configuration system.

## 5. Provider Integration Architecture

Design a common provider integration contract with channel-specific capabilities.

The architecture should support:

- Provider configuration validation.
- Credential verification, where supported.
- Connection or health checks, where supported.
- Payload validation.
- Provider-specific request construction.
- Submission of supported delivery operations.
- Parsing provider responses.
- Normalization of provider errors.
- Delivery-status lookup, where available.
- Webhook event validation and processing.
- Provider-specific rate limits and operational constraints.
- Safe handling of provider timeouts and ambiguous outcomes.

Use a consistent internal delivery interface so campaign execution does not depend directly on vendor-specific request formats.

Provider-specific behavior belongs in dedicated adapters or services.

A provider adapter must explicitly declare which capabilities it supports. Do not assume all providers support scheduling, bulk delivery, delivery receipts, unsubscribe callbacks, campaign analytics, or status lookup.

### Required abstraction boundaries

Keep the following concepts distinct:

- Marketing campaign.
- Campaign channel configuration.
- Provider connection.
- Delivery run or execution batch.
- Recipient delivery record.
- Provider request or message identifier.
- Provider event.
- Normalized delivery status.

Use existing entities where available and introduce new entities only where a verified gap exists.

Avoid a monolithic service containing all provider-specific logic.

## 6. Provider Integrations

Inspect the existing codebase and select an implementation strategy based on actual available infrastructure and supported providers.

Implement one or more real provider adapters where the repository, approved configuration, and available credentials make this feasible.

Potential integrations include email delivery providers, SMS gateways, business messaging providers, and advertising APIs. Choose concrete providers based on project requirements and existing dependencies rather than guessing.

For each implemented provider, include:

- Configuration and setup instructions.
- Credential validation.
- Required sender or account configuration.
- Payload mapping.
- Submission and response handling.
- Error normalization.
- Retry and idempotency behavior appropriate to the provider.
- Delivery status updates where supported.
- Webhook verification and processing where supported.
- Automated tests, including mocked provider responses.
- A clear description of capabilities and limitations.

If credentials are unavailable, implement the adapter and test suite using a documented mock or test environment where appropriate, but clearly identify the integration as **not live-verified**.

Never report a test submission as a real delivery.

Do not add every possible provider just to increase the number of integrations. Prefer a small number of reliable, maintainable implementations.

## 7. Secure Provider Credential Management

Provider credentials must be managed securely.

Requirements:

- Reuse the application's existing secret-management system.
- Prefer environment-based secrets, a secret manager, or an existing encrypted credential mechanism.
- Never commit API keys, passwords, access tokens, private keys, or webhook secrets.
- Never expose secret values in API responses, UI pages, logs, exception messages, or audit events.
- Mask sensitive credential fields in the interface.
- Restrict credential creation, editing, testing, and rotation to authorized users.
- Separate tenant-specific credentials where the business model requires it.
- Apply least-privilege provider permissions.
- Support credential rotation without requiring a full application redeployment when existing infrastructure permits.
- Avoid storing credentials in ordinary configuration JSON or plaintext database fields.
- Redact sensitive provider request and response fields before logging.

If the repository lacks a safe credential-storage mechanism, document the gap and implement an appropriate integration boundary rather than introducing insecure plaintext storage.

Provider credentials must never be accessible to ordinary campaign operators unless explicitly required by an established authorization model.

## 8. Campaign-to-Channel Configuration

Extend the existing Phase 08 campaign workflow to support channel configuration.

Authorized users should be able to:

- Select a supported channel.
- Select a valid provider connection.
- Configure the sender identity or provider account, where applicable.
- Review provider capabilities and configuration status.
- Validate channel-specific prerequisites.
- Associate a prepared audience from Phase 09.
- Preview delivery eligibility and expected recipient counts.
- Schedule or initiate an authorized delivery run.
- View delivery status and errors.

Enforce valid campaign lifecycle transitions using the existing campaign lifecycle.

Do not bypass existing approvals or introduce a duplicate campaign approval framework.

Where the existing application supports campaign approvals, require the relevant approval before execution.

Keep the campaign record separate from individual delivery runs so that a campaign can have multiple channels, execution batches, or retries without overwriting its history.

A campaign status of active or approved must not automatically trigger external delivery unless an explicit, authorized execution action or established scheduling rule requires it.

## 9. Audience Preparation Using Phase 09

Use the existing audience segmentation and targeting implementation.

Support appropriate audience sources, including:

- A saved dynamic segment.
- A specific persisted segment membership snapshot.
- A static segment.
- Multiple segments, if the existing Phase 09 implementation supports them reliably.
- Explicit exclusions supported by the existing segmentation model.

Before execution:

1. Resolve the selected audience using authoritative Phase 09 services.
2. Determine whether the campaign references a live segment definition or a persisted snapshot.
3. Apply the campaign's agreed audience policy.
4. Deduplicate recipients using appropriate canonical identity rules.
5. Validate that source records still exist and are eligible for the selected channel.
6. Apply consent, opt-out, suppression, and communication preference rules.
7. Validate required channel-specific contact information.
8. Produce a delivery eligibility summary.
9. Record the segment version or snapshot reference used by the delivery run.

For reproducible execution, prefer a defined membership snapshot when the campaign requires a stable audience. If live dynamic membership is permitted, explicitly record the evaluation and membership state used for that run.

Do not silently substitute a different audience if a referenced snapshot or segment becomes unavailable.

Do not create duplicate customer, contact, lead, or account records.

## 10. Consent, Suppression, and Recipient Eligibility

Implement a centralized recipient eligibility interface that channel adapters and execution services must use.

Reuse the existing consent, preference, unsubscribe, and suppression systems.

Eligibility checks should consider the requirements applicable to the selected channel and operation, including:

- Whether the contact is eligible for the intended communication.
- Existing consent or other applicable authorization records.
- Unsubscribe and opt-out status.
- Suppression lists.
- Channel-specific preferences.
- Valid contact information.
- Existing restrictions on inactive or deleted records.
- Relevant tenant, organization, and data-access restrictions.
- Any provider-required sender or recipient constraints.

Do not assume that eligibility for one channel implies eligibility for another.

Do not treat a generic customer relationship, a segment membership, a previous purchase, or an available email address or phone number as automatic consent.

If authoritative consent information is unavailable, do not fabricate consent status or silently bypass the requirement. Mark eligibility as unknown or unverifiable and block the affected execution when necessary to meet applicable policy or law.

Record exclusion counts and appropriate reason codes without exposing unnecessary personal information.

Apply eligibility checks as close as practical to execution, since preferences and consent may change after an audience snapshot is created.

Implement a reliable unsubscribe or suppression update pathway when supported by the existing consent infrastructure. Provider callbacks must not be allowed to override stronger authoritative restrictions.

This phase must not create an independent, conflicting consent database.

## 11. Delivery Planning and Execution

Implement a controlled delivery execution service.

A delivery run should capture applicable information such as:

- Campaign reference.
- Channel configuration.
- Provider connection reference.
- Audience segment and snapshot reference.
- Campaign or message configuration version.
- Requested execution time and time zone.
- Execution initiator.
- Approval reference, where applicable.
- Planned recipient count.
- Eligible recipient count.
- Excluded recipient count.
- Submitted, accepted, delivered, failed, and pending counts where supported.
- Start and completion timestamps.
- Execution status and failure details.

Use a suitable lifecycle, adapted to existing conventions, such as:

- Draft.
- Validating.
- Scheduled.
- Queued.
- Running.
- Partially completed.
- Completed.
- Failed.
- Cancelled.

Define transitions and ensure invalid transitions are rejected server-side.

Scheduling must use the existing scheduler or job infrastructure. Respect time zones and prevent duplicate execution caused by repeated scheduler triggers.

Support cancellation where operationally possible, but clearly distinguish cancellation of pending work from messages already submitted to a provider.

Once a provider has accepted a message, do not claim it was recalled unless the provider explicitly confirms a supported cancellation.

Do not hold long-running provider operations inside a user-facing HTTP request.

## 12. Recipient Delivery Records and Status Lifecycle

Track delivery at the appropriate granularity.

For recipient-level channels, persist a delivery record or equivalent durable state for each intended recipient and execution attempt, using the repository's established data model where possible.

Separate recipient delivery state from aggregate campaign and run status.

A normalized lifecycle may include:

- Pending.
- Queued.
- Submitting.
- Accepted by provider.
- Sent, when the provider supplies evidence for that status.
- Delivered, when the provider confirms delivery.
- Bounced or rejected.
- Failed.
- Suppressed or skipped.
- Cancelled before submission.
- Unknown outcome requiring reconciliation.

Do not treat provider acceptance as equivalent to delivery.

Do not treat a successful HTTP response as proof that the recipient received a message.

Support provider-specific state mapping and retain the original provider status where useful for troubleshooting.

Record provider message identifiers and correlate subsequent delivery events with the correct recipient and execution run.

For channels that do not provide recipient-level delivery receipts, record the available evidence and represent unavailable statuses honestly.

For advertising or other campaign-level APIs, use the provider's appropriate operation-level status model rather than forcing the integration into an email-style recipient model.

## 13. Idempotency, Retries, and Ambiguous Outcomes

Prevent accidental duplicate sends.

Requirements:

- Generate stable internal identifiers for delivery runs and delivery operations.
- Use provider-supported idempotency keys when available.
- Enforce appropriate uniqueness constraints for recipient/run operations.
- Make job handlers safe to retry.
- Distinguish definite failure from an ambiguous provider outcome.
- Use bounded exponential backoff with jitter where appropriate.
- Respect provider retry instructions and rate limits.
- Stop retrying permanent errors.
- Make retry attempts visible and auditable.
- Support reconciliation when a request may have succeeded but the response was lost.

### Critical timeout behavior

If a provider request times out after submission may have occurred, do not automatically resend the same message blindly.

First, use a provider-supported idempotency mechanism, status lookup, or other documented reconciliation strategy when available.

If the outcome cannot be determined, mark it as unknown and route it through a safe recovery path. Avoid silently creating duplicate deliveries.

Ensure that a repeated queue message, duplicate webhook, application restart, or scheduler retry cannot cause uncontrolled duplicate sends.

Use distributed locks or concurrency controls where appropriate to prevent two workers from executing the same delivery operation simultaneously.

## 14. Provider Rate Limits and Throughput

Implement provider-aware rate limiting and workload controls.

Support where appropriate:

- Per-provider and per-account rate limits.
- Concurrency limits.
- Batch-size limits.
- Queue backpressure.
- Provider retry-after handling.
- Temporary provider-unavailable states.
- Circuit-breaking or equivalent protection for persistent provider failures.
- Monitoring of throttling and delivery latency.

Do not hard-code a universal throughput limit for every provider. Use verified provider capabilities and configurable application safeguards.

Ensure that a large campaign cannot exhaust database connections, overwhelm workers, or block unrelated ERP functions.

Avoid logging complete recipient lists or sensitive payloads merely to diagnose throughput problems.

## 15. Inbound Webhooks and Provider Events

Implement a secure webhook framework for providers that support callbacks.

Requirements:

1. Validate signatures, authentication tokens, or other documented verification mechanisms.
2. Use timestamp and replay protection where supported.
3. Validate payload structure and size.
4. Deduplicate webhook events using provider event identifiers or equivalent stable keys.
5. Persist or otherwise durably record events before acknowledging receipt when required by the architecture.
6. Process events asynchronously where appropriate.
7. Correlate events with provider message IDs and internal delivery records.
8. Normalize event types into the application's delivery-state model.
9. Preserve original provider event types where useful for troubleshooting.
10. Handle out-of-order and repeated events safely.
11. Apply valid unsubscribe or suppression updates through the authoritative existing consent mechanisms.
12. Avoid exposing provider secrets or personal information in logs.

Never trust a webhook merely because it contains a valid-looking message identifier.

Do not allow unauthenticated or unverified callbacks to mark a message delivered, alter campaign state, or change recipient eligibility.

If a provider lacks webhook support, use its supported status-query mechanism where available or explicitly document that delivery tracking is limited.

## 16. Channel-Specific Validation and Content Handling

The content editor and asset library are outside this phase except where minimal interfaces are required to submit a delivery through an existing mechanism.

Validate channel-specific payload requirements before execution.

Examples include:

- Email sender, recipient, subject, and content requirements.
- SMS recipient formatting and supported message length.
- Messaging-provider templates, approved sender identities, and template identifiers where required.
- Advertising account, campaign, audience, or creative references required by the selected provider.

Do not implement a separate full template or asset management system; that belongs to Phase 11.

Where an existing content source is available, reference it using canonical identifiers.

Do not duplicate asset files or templates unnecessarily.

Do not silently truncate or materially transform content without making the behavior explicit and validating the resulting payload.

Handle provider-specific formatting, character limits, encoding, and unsupported features within the appropriate adapter.

## 22. Explicitly Out of Scope

Do not implement the following in Phase 10:

- Full marketing asset and template management — **Phase 11**.
- Full promotions and offers management.
- Advanced marketing budget management — **Phase 12**.
- Campaign attribution, conversion attribution, and ROI analytics — **Phase 13**.
- A generic advanced bulk-operation framework beyond what delivery execution requires — **Phase 14**.
- Advanced cross-module workflow orchestration — **Phase 15**.
- A broad external integration marketplace, public developer platform, or generalized webhook ecosystem beyond the requirements of implemented providers — **Phase 16**.
- Advanced business intelligence — **Phase 17**.
- AI-generated content, predictive targeting, or AI-assisted marketing — **Phase 18**.
- A duplicate CRM, contact, customer, campaign, or audience management module.
- A replacement consent, unsubscribe, or suppression system.
- A duplicate finance, payment, or sales order module.

Do not implement future-phase functionality prematurely.

## 23. Recommended Implementation Sequence

Proceed in the following order:

1. Inspect the repository and document the existing integration, campaign, segmentation, security, and job infrastructure.
2. Identify missing capabilities and select a realistic initial set of provider integrations.
3. Define channel, provider, delivery-run, and delivery-status abstractions.
4. Implement the secure provider configuration and credential-management boundary.
5. Implement the common provider adapter interface.
6. Implement the first complete provider adapter or adapters supported by the repository.
7. Implement campaign-to-channel configuration using Phase 08.
8. Integrate audience resolution, snapshots, and eligibility checks using Phase 09.
9. Implement durable delivery runs and execution through the existing background-job infrastructure.
10. Implement idempotency, rate limits, retries, ambiguous-outcome handling, and recovery.
11. Implement delivery-state tracking and provider event processing.
12. Implement verified webhook handling where supported.
13. Build provider configuration, campaign channel setup, and execution-monitoring UI.
14. Add permissions, audit events, operational metrics, and documentation.
15. Run unit, integration, security, and regression tests.
16. Review the result for duplicate sends, privacy issues, insecure credential handling, tenant leakage, and scope creep.

Adapt the order to the actual repository, but preserve the security requirements and acceptance criteria.

## 24. Acceptance Criteria

Phase 10 is complete only when the following criteria are met or explicitly documented as blocked by verified dependencies:

- [ ] Marketing channels and provider connections use a reusable architecture.
- [ ] Provider-specific logic is isolated behind clear adapter interfaces.
- [ ] Provider credentials are securely managed and never exposed in plaintext through application interfaces or logs.
- [ ] At least one complete real provider adapter is implemented where the repository and approved configuration make this feasible; any unverified integration is clearly labeled.
- [ ] Campaigns can be configured for supported channels using the existing Phase 08 campaign model.
- [ ] Delivery execution uses existing Phase 09 segments and snapshots.
- [ ] Recipient eligibility and available consent, opt-out, and suppression checks are enforced.
- [ ] Unknown consent status is not silently treated as permission to communicate.
- [ ] Delivery runs and individual delivery states are recorded durably.
- [ ] Provider acceptance and confirmed recipient delivery are represented as distinct statuses.
- [ ] Retries, ambiguous timeouts, and repeated jobs cannot cause uncontrolled duplicate sends.
- [ ] Provider rate limits and workload limits are enforced appropriately.
- [ ] Supported webhooks are authenticated, deduplicated, and processed safely.
- [ ] Execution failures, provider responses, and recovery actions are traceable.
- [ ] UI and APIs enforce permissions, tenant isolation, and privacy requirements.
- [ ] Tests cover successful execution, failure, recovery, security, and regressions.
- [ ] Documentation explains configuration, credential setup, supported capabilities, limitations, and deployment.
- [ ] Existing Phases 01–09 remain functional.
- [ ] No duplicate CRM, campaign, segment, consent, or other ERP module has been created.
- [ ] No Phase 11 or later functionality has been implemented prematurely.

## 25. Final Implementation Report

After implementation, provide a detailed report containing:

1. **Summary:** What was implemented and what remains incomplete.
2. **Architecture:** Channel registry, provider adapters, execution pipeline, and status lifecycle.
3. **Provider coverage:** Exact providers implemented, capabilities supported, setup requirements, and whether each was tested against a real provider or only mocks.
4. **Files changed:** Important new and modified files.
5. **Database changes:** Migrations, entities, indexes, and constraints.
6. **API changes:** Endpoints, request validation, and authorization.
7. **UI changes:** Screens, workflows, and navigation.
8. **Security:** Credential storage, consent safeguards, tenant isolation, webhook verification, and privacy protections.
9. **Reliability:** Idempotency, retries, rate limiting, reconciliation, and recovery.
10. **Testing:** Exact commands executed and their actual outcomes, including failures and skipped tests.
11. **Deployment:** Required environment variables, secrets, migrations, webhook setup, and provider configuration.
12. **Limitations:** Missing credentials, unavailable provider capabilities, incomplete integrations, and known technical debt.
13. **Acceptance criteria:** Mark each item as passed, failed, or blocked, with supporting evidence.
14. **Phase 11 readiness:** Explain how the channel execution architecture can consume reusable assets and templates in the next phase.

Do not state that a provider is operational if credentials, sandbox testing, or necessary setup are still missing. Distinguish implemented code from live-verified functionality.

## Final Instruction

Implement **Phase 10 only**. Inspect the actual repository and Phases 01–09 before changing code. Make real repository changes where the coding environment permits, reuse existing architecture, execute available tests, and report verified outcomes honestly.

Prioritize secure credential management, recipient eligibility, provider abstraction, delivery-state accuracy, idempotency, and safe recovery.

The finished result must be a production-oriented, industry-agnostic marketing channel integration capability that is ready for **Phase 11: Marketing Assets, Templates, and Content**, without prematurely implementing later phases.
