# Phase 08: Marketing Foundation and Campaign Management

## Role and Implementation Approach

Act as a senior ERP architect, business analyst, marketing operations specialist, database architect, backend engineer, frontend engineer, and QA engineer.

Implement **Phase 08: Marketing Foundation and Campaign Management** in the existing ERP repository.

The ERP is intended to support businesses across multiple industries. Marketing terminology, campaign types, workflows, metrics, and configuration must remain industry-agnostic. Do not introduce assumptions specific to garment manufacturing, textiles, or any other individual industry.

This is one phase in a larger Sales & Marketing implementation. Extend the existing ERP using its established architecture, data models, authorization, reporting, audit, and integration patterns.

### Sources of truth

Use the following sources in order:

1. Existing repository architecture, technical documentation, and coding conventions.
2. The Sales & Marketing Feature Requirements Document.
3. The actual implementations of Phases 01–07.
4. The requirements in this prompt.

Before coding, inspect the repository and identify existing capabilities for:

- Sales & Marketing foundation and navigation.
- CRM, customers, contacts, enquiries, and sales ownership.
- Sales Orders and existing transaction references.
- Sales channels, where implemented in Phase 07.
- User, employee, organization, and permission management.
- Existing campaign, marketing, email, notification, or communication functionality.
- Reporting, analytics, audit trails, events, background jobs, and file storage.
- Existing approval workflows and reusable UI components.

Do not assume previous phases were implemented exactly as expected. Verify their actual data models and integration interfaces.

Reuse existing functionality wherever possible. Do not create duplicate CRM entities, communication systems, user management, reporting platforms, or other ERP modules.

## 1. Phase Objective

Establish a reusable Marketing foundation and implement a comprehensive campaign management capability.

Authorized users must be able to:

- Access Marketing through the existing ERP navigation.
- Configure and manage marketing campaigns.
- Organize campaigns by type, objective, status, owner, channel, and time period.
- Plan campaign schedules and milestones.
- Manage campaign lifecycle and approvals.
- Define campaign objectives and measurable success criteria.
- Record planned campaign activities and execution status.
- Associate campaigns with existing CRM and sales entities where appropriate.
- Track campaign-level planned and actual expenditure when reliable data is available.
- Maintain campaign history, changes, and audit trails.
- View campaign summaries and basic performance indicators.
- Integrate campaigns with existing permissions, reporting, and background processing.
- Establish clean interfaces for future marketing phases.

The foundation must support both simple campaigns and more structured multi-stage campaigns without forcing every business to use the same marketing process.

## 6. Campaign Lifecycle and Status Management

Implement a clear and validated campaign lifecycle.

A possible lifecycle includes:

- Draft.
- In planning.
- Pending approval.
- Approved.
- Scheduled.
- Active.
- Paused.
- Completed.
- Cancelled.
- Archived.

Adapt the actual states to the repository's workflow conventions.

Do not implement every proposed status if it does not provide a useful distinction.

### Requirements

- Validate allowed status transitions on the server.
- Restrict transitions according to permissions.
- Prevent unauthorized activation, cancellation, or completion.
- Define how start and end dates affect lifecycle transitions.
- Preserve historical status changes.
- Distinguish planned dates from actual execution.
- Prevent invalid date ranges.
- Define behavior when a campaign is paused or rescheduled.
- Prevent accidental deletion of campaigns with historical activity or financial references.
- Preserve completed and cancelled campaign records for audit and reporting.

If workflow automation already exists, reuse it. Otherwise, implement a minimal, explicit transition service.

Do not build a general-purpose workflow engine in this phase.

### Scheduled activation

If the repository already supports scheduled jobs, allow campaigns to transition according to configured scheduling rules where appropriate.

Scheduled transitions must be safe to retry and must not trigger external campaign execution. Channel execution belongs to Phase 10.

Do not claim a campaign has been launched externally merely because its status changes to Active.

## 7. Campaign Objectives and Success Criteria

Provide a structured way to define what a campaign intends to achieve and how its success will be evaluated.

### 7.1 Objective configuration

Support one or more objectives per campaign where appropriate.

Examples may include:

- Lead generation.
- Customer engagement.
- Brand awareness.
- Product or service awareness.
- Customer retention.
- Sales growth.
- Event participation.
- Website traffic.
- Channel engagement.

These are examples, not a mandatory fixed industry taxonomy.

Allow administrators to configure categories and objective definitions where appropriate.

### 7.2 Success metrics

Support configurable campaign success criteria using defined metric types.

Examples may include:

- Number of enquiries generated.
- Number of qualified leads, if the existing CRM supports that state.
- Number of responses.
- Number of participants or registrations, if relevant source data exists.
- Sales Orders attributed through an explicitly supported relationship.
- Invoiced sales value, if Finance data is available.
- Engagement or reach metrics, if a trusted source exists.
- Other configurable measurable outcomes.

Do not expose a metric as automatically calculated when the necessary source data or integration does not exist.

For each metric, define:

- Metric name and description.
- Measurement unit.
- Target value, if applicable.
- Authoritative source.
- Calculation method.
- Applicable period.
- Whether it is manually reported or system-calculated.
- Validation rules.
- Known limitations.

Keep planned targets distinct from measured actuals.

Do not implement advanced multi-touch attribution or definitive campaign ROI calculations in this phase.

### 7.3 Metric provenance

Where a campaign metric is calculated from existing ERP records, retain the relevant source references or calculation provenance.

Where a metric is manually reported, clearly identify it as manually entered and audit changes.

Do not represent unverified manual values as authoritative system-calculated metrics.

- Currency.
- Budget notes.
- Budget approval status.

Do not implement advanced financial forecasting, promotional funding, or multi-dimensional budget allocation in this phase.

## 18. Performance and Scalability

Design for growing numbers of campaigns, activities, and historical records.

- Avoid N+1 queries.
- Use pagination for campaign lists and activity histories.
- Add indexes for common status, date, owner, team, and tenant filters.
- Avoid loading entire CRM or transaction datasets into memory.
- Use efficient aggregation queries.
- Bound report date ranges where appropriate.
- Use existing caching and background processing only when justified.
- Keep campaign dashboard requests efficient.
- Avoid recalculating historical data unnecessarily.
- Make failures in scheduled operations visible to authorized users.

Do not introduce unnecessary infrastructure for hypothetical future requirements.
