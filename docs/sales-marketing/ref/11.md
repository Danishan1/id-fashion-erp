# Phase 11: Marketing Assets, Templates, and Content

## 1. Objective

Implement a production-oriented, industry-agnostic **Marketing Assets, Templates, and Content Management** capability within the existing Sales & Marketing ERP module.

The objective is to let authorized users create, organize, upload, edit, reuse, version, review, approve, and manage marketing content and assets. Approved content should be reusable by campaigns and compatible with the channel execution infrastructure implemented in Phase 10.

The module should support a variety of business needs without industry-specific assumptions. Do not introduce garment-, textile-, manufacturing-, or other industry-specific terminology, entities, or workflows.

The system must distinguish between:

- A reusable content asset.
- A reusable message template.
- A campaign-specific content instance.
- A content version.
- An approval decision.
- A provider-ready delivery payload.

These concepts must remain separate so changes to a reusable template do not silently modify content already approved or scheduled for delivery.

Before making changes:

1. Inspect the repository architecture, coding conventions, existing documentation, tests, and deployment requirements.
2. Review the Sales & Marketing Feature Requirements Document and the work implemented in Phases 01–10.
3. Identify existing implementations for:
   - Campaigns and campaign approvals.
   - Marketing channels, provider adapters, delivery runs, and channel-specific validation.
   - Audience segments and snapshots.
   - File uploads and storage.
   - Document management and reusable attachments.
   - Rich-text editors and content rendering.
   - Template systems, localization, and translation.
   - Background jobs and asynchronous processing.
   - Authentication, authorization, tenant isolation, and access control.
   - Audit logging, version history, and approval workflows.
   - Malware scanning, file validation, and content-security controls.
4. Reuse existing storage, authorization, document, and workflow infrastructure where appropriate.
5. Determine which content formats can actually be supported by the current application and Phase 10 provider adapters.

Do not assume that a file-storage service, image-processing service, template renderer, or approval engine exists without verifying it.

If a required dependency is missing, document the gap and implement a safe integration boundary where practical. Do not introduce duplicate infrastructure unnecessarily.

Implement the following capabilities:

1. Marketing asset library.

## 4. Marketing Asset Library

Create a centralized library for reusable marketing assets.

Depending on the repository's existing capabilities, supported asset types may include:

- Images and illustrations.
- Logos and brand graphics.
- PDFs and approved downloadable documents.
- Video files or video references.
- Documents and other approved file types.
- External asset references where secure and appropriate.

Do not claim that every file format is previewable or renderable. Clearly distinguish between supported upload, preview, transformation, and delivery capabilities.

### Asset metadata

Support appropriate fields such as:

- Asset name.
- Unique identifier.
- Description.
- Asset type and MIME type.
- File size.
- Storage reference.
- Original filename, where safe to retain.
- Dimensions or duration when available.
- Tags and categories.
- Owner or responsible team.
- Created and updated timestamps.
- Tenant or organizational scope.
- Lifecycle status.
- Version reference.
- Accessibility text or alt text for applicable assets.
- License, usage restrictions, or expiry metadata where required by the business.
- Checksum or content hash where useful for integrity and duplicate detection.

Use existing tagging and metadata facilities where available.

### Asset operations

Provide authorized users with the ability to:

- Upload assets.
- View asset metadata.
- Search, filter, sort, and paginate the asset library.
- Update editable metadata.
- Preview supported formats.
- Download assets when authorized.
- Organize assets with tags or categories.
- Archive assets.
- View version history.
- Replace an asset through a new version instead of silently overwriting referenced content.

Do not create a second general-purpose document management system.

## 5. Secure File Handling

Implement secure upload and storage behavior using existing infrastructure.

Requirements:

- Validate file size against configurable limits.
- Validate allowed file types using content inspection where supported, not only filename extensions.
- Generate safe storage keys rather than trusting user-supplied filenames as paths.
- Prevent path traversal and unsafe filename handling.
- Use private storage by default unless public delivery is explicitly required.
- Restrict uploads, downloads, previews, and deletion by authorization and tenant boundaries.
- Apply malware scanning or an existing file-inspection workflow where available.
- Prevent unsafe HTML, script, and active-content execution during preview.
- Avoid serving uploaded files directly from privileged application origins when doing so could create a security risk.
- Use short-lived signed URLs or equivalent protected delivery mechanisms when appropriate.
- Enforce safe download headers and content types.
- Avoid logging sensitive file contents or signed URLs.
- Record file size, checksum, and relevant processing status.
- Handle interrupted uploads and failed storage operations safely.

If malware scanning is unavailable, document the limitation and ensure the system does not falsely report that uploaded content has been scanned.

Do not store large files directly in the database unless the existing architecture explicitly requires it.

## 6. Asset Lifecycle and Versioning

Support a lifecycle appropriate to reusable marketing assets, such as:

- Draft or pending processing.
- Available for review.
- Approved, where required.
- Active or available.
- Archived.
- Rejected or quarantined, where supported.

Use existing lifecycle conventions where possible.

When an asset is replaced:

1. Create a new version or immutable revision.
2. Preserve the identity and history of the prior version.
3. Retain references from existing campaigns and content versions.
4. Validate the new version before making it available.
5. Apply approval requirements where configured.
6. Prevent a replacement from silently changing already approved or scheduled content.

Represent file processing failures explicitly.

Do not delete an asset version while it is referenced by an active campaign, approved template, or delivery record unless a safe, authorized retention process permits it.

## 7. Reusable Marketing Templates

Implement a reusable template library for channel-compatible content.

Examples include:

- Email message templates.
- SMS message templates.
- Business messaging templates where supported.
- General marketing copy blocks.
- Reusable headlines and calls to action.
- Structured content sections.
- Reusable image and document references.

These are examples; actual template formats must match the capabilities of the application and configured Phase 10 providers.

### Template metadata

Support appropriate fields such as:

- Template name.
- Unique code or identifier.
- Description.
- Channel or intended usage.
- Content format.
- Owner and organizational scope.
- Language or locale.
- Tags and categories.
- Status.
- Current version.
- Approval status.
- Creation and update timestamps.
- Optional expiry or review date.

Templates must be reusable across campaigns without creating separate copies of the underlying template definition for every use.

## 8. Content Editor and Authoring

Build an authoring interface appropriate to the existing frontend architecture.

Support the content formats that can be safely validated, previewed, and rendered by the application.

Possible formats include:

- Plain text.
- Structured rich text.
- HTML email content.
- SMS text.
- Structured messaging content supported by a configured provider.
- Reusable content blocks.

Use an existing editor if available. Do not build a complex rich-text editing engine from scratch without a clear need.

### Authoring requirements

Users should be able to:

- Create a template.
- Edit an editable draft.
- Save drafts without publishing them.
- Preview the content.
- Validate required fields and supported content structures.
- View the current version and approval state.
- Duplicate a template as a starting point.
- Create a new version from an existing approved version.
- Compare versions where the existing architecture supports it.
- Archive templates when permitted.

Validate content on the server as well as in the UI.

Treat user-authored HTML and external content as untrusted. Apply an appropriate sanitization policy and prevent script execution, unsafe embedded resources, and other active-content risks.

Do not allow arbitrary template code or unrestricted server-side execution.

## 9. Template Variables and Personalization

Support controlled, typed template variables for personalization.

Examples may include:

- Recipient display name.
- Organization or account name.
- Campaign name.
- Approved business attributes.
- Links generated through trusted application services.
- Other fields explicitly exposed by authorized data-source integrations.

Only expose fields that exist, are authorized for use, and are appropriate for the intended channel.

### Variable definition

For each supported variable, define appropriate metadata:

- Variable key.
- Display label.
- Data type.
- Source field or approved resolver.
- Required or optional status.
- Default or fallback behavior, if allowed.
- Validation rules.
- Whether it is safe for use in the selected channel.

### Rendering safeguards

- Resolve variables through a controlled allowlist.
- Enforce tenant and field-level authorization.
- Escape values according to the output context.
- Prevent HTML injection and script injection.
- Prevent arbitrary database queries or code execution through variable expressions.
- Define clear behavior for missing or invalid values.
- Validate required values before scheduling or execution.
- Ensure text substitutions do not break channel-specific formatting.
- Avoid exposing sensitive CRM fields to content authors who lack permission to access them.

Do not treat a missing variable as an empty string without an explicit rule. Surface unresolved required variables as validation errors.

Personalization should be deterministic for a given content version and input set.

## 10. Channel-Specific Content Validation

Integrate with the provider capability and validation interfaces implemented in Phase 10.

Each template or content instance must identify the intended channel and supported content format.

Validate applicable requirements such as:

- Required subject and body fields for email.
- Supported character length and encoding for SMS.
- Approved template identifiers or structural requirements for messaging providers.
- Supported attachments and file formats.
- Sender or provider constraints.
- Unsupported markup or content components.
- Required links, variables, and fallback values.

Use provider adapters to perform provider-specific validation when supported.

Do not assume that a template valid for one provider is automatically valid for another provider using the same channel.

Distinguish between:

- Locally validated content.
- Content validated against a provider's rules.
- Content submitted to a provider for approval.
- Content approved by an external provider.
- Content approved internally by the organization.

Do not claim external provider approval unless an authoritative provider response confirms it.

## 11. Content Preview and Test Rendering

Provide a safe preview experience.

Support applicable preview modes, including:

- Rendered template preview.
- Preview using sample data.
- Preview using an authorized test record.
- Preview with selected channel settings.
- Desktop or mobile preview where supported by the renderer.
- Display of unresolved variables.
- Validation warnings.
- Content-length and format warnings.

Test-record previews must respect permissions and avoid exposing personal data to unauthorized users.

Use synthetic sample data by default when real records are unnecessary.

Ensure that preview rendering does not send real messages or trigger external provider actions.

Where provider test or preview APIs are available, keep those operations explicitly separate from real campaign delivery.

## 12. Content Approval and Review Workflow

Reuse the existing approval and workflow infrastructure.

Support configurable review steps appropriate to the repository, such as:

- Draft.
- Submitted for review.
- In review.
- Changes requested.
- Approved.
- Rejected.
- Archived.

Implement only the workflow complexity justified by existing architecture.

Record:

- Reviewer and approver identities.
- Decision.
- Timestamp.
- Comments or reason.
- Content version reviewed.
- Relevant revision identifier.

Enforce permissions server-side.

Only authorized reviewers may approve content. Authors must not gain approval authority automatically unless existing policy explicitly permits it.

If an approved version changes, create a new version and apply the appropriate review process again.

Approval must apply to a specific immutable content version, not merely to a mutable template identifier.

Do not implement a separate approval engine if the existing ERP provides one.

## 13. Campaign-Specific Content Instances

Integrate templates and assets with the existing Phase 08 campaign model and Phase 10 delivery infrastructure.

A campaign should be able to reference reusable templates and approved assets, then create or maintain a campaign-specific content instance when necessary.

Support:

- Selecting an existing template.
- Referencing specific template and asset versions.
- Creating campaign-specific content from a template.
- Overriding permitted fields without modifying the shared template.
- Validating the resulting content for the selected channel.
- Tracking approval status for the campaign-specific content.
- Viewing which versions were used by a campaign or delivery run.
- Preserving historical content when a shared template is subsequently changed.

### Critical versioning rule

When a campaign is prepared for delivery, preserve a stable reference or immutable snapshot of the approved content version and relevant asset versions.

A later template edit must not silently alter the content associated with an already approved or scheduled delivery.

If content is modified after approval, determine whether the change invalidates approval or requires reapproval according to the existing workflow.

Do not overwrite historical content that is needed to investigate a prior delivery.

## 14. Integration with Phase 10 Delivery

Expose content to the existing channel execution layer through clear service interfaces.

The Phase 10 delivery system should be able to obtain:

- The selected content or template version.
- The resolved channel and content format.
- Approved asset references.
- Validated personalization variables.
- A rendered payload appropriate to the provider adapter.
- Validation results and actionable errors.
- Content and asset version identifiers for auditability.

Before delivery, verify that:

- The content version exists and is accessible.
- Required approval is present.
- The selected provider supports the content format.
- Required variables can be resolved.
- Required assets are available.
- The content has not expired or been invalidated by a relevant policy.
- The content complies with the applicable channel constraints.

Keep content rendering separate from delivery execution.

Do not duplicate provider adapters, delivery-run records, recipient delivery records, or delivery-status tracking.

Do not send messages or launch campaigns merely because content has been saved, approved, or published.

Real delivery remains under the explicit execution controls and eligibility safeguards established in Phase 10.

## 15. Localization and Language Support

Where compatible with the existing architecture, support multiple language or locale variants for reusable templates.

Requirements may include:

- Template language and locale.
- A relationship between translations and their source template.
- Separate versioning and approval for each localized version.
- Fallback rules when a requested locale is unavailable.
- Validation that required localized content exists before delivery.
- Clear indication of which locale was selected for a delivery run.

Do not assume automatic translation is available.

Do not introduce machine-generated translation or AI content creation in this phase.

If the existing application lacks localization infrastructure, implement only the minimal metadata and extension points required for future support and document the limitation.

## 16. Asset Search, Reuse, and Governance

Provide efficient asset and template discovery.

Support applicable features such as:

- Search by name and description.
- Filtering by channel, type, status, owner, language, or category.
- Tag-based search.
- Sorting and pagination.
- Identification of reusable or deprecated content.
- Reference counts or usage history where available.
- Identification of assets referenced by campaigns or templates.
- Warnings before archiving or replacing in-use assets.

Do not build a duplicate enterprise-wide search engine.

Reuse the application's existing search infrastructure where available.

Ensure that search results respect tenant isolation, permissions, and access restrictions.

Implement appropriate operations for:

- Listing, uploading, retrieving, updating, and archiving assets.
- Retrieving asset versions and usage references.
- Creating and managing templates.
- Creating new content versions.
- Saving drafts and submitting content for review.
- Approving, rejecting, or requesting changes.
- Validating templates and variables.
- Rendering safe previews.
- Managing supported localization variants.
- Creating campaign-specific content instances.
- Resolving approved content for the Phase 10 delivery layer.
- Retrieving validation and approval history.

Enforce authentication, authorization, tenant isolation, input validation, and consistent error responses.

Use pagination for library and history endpoints.

Use secure upload and download mechanisms.

Do not expose raw storage credentials, internal storage paths, private signed URLs beyond their intended scope, or unrestricted personal data.

Long-running file processing, scanning, or rendering should use existing background-job infrastructure where appropriate.

## 19. Security, Audit, and Operational Reliability

### Security

Enforce:

- Tenant isolation.
- Role-based and resource-level permissions.
- Secure file upload and download.
- Safe HTML and content sanitization.
- Safe variable resolution.
- Protection against injection and unsafe file handling.
- Secret redaction.
- Access control for previews and downloads.
- Appropriate handling of external links and embedded content.

### Audit

Record important operations, including:

- Asset uploads and metadata changes.
- New asset versions.
- Template creation and modification.
- Content version creation.
- Approval decisions.
- Campaign content selection.
- Content overrides.
- Archival and deletion attempts.
- Content validation outcomes where operationally useful.

Record the actor, timestamp, relevant identifiers, and decision or change details, while avoiding unnecessary personal information and sensitive content in logs.

### Reliability

Handle:

- Failed uploads.
- Failed file scanning or processing.
- Invalid or unsupported formats.
- Rendering failures.
- Missing variables.
- Missing or archived asset references.
- Concurrent content edits.
- Conflicting approval decisions.
- Failed migrations or partial operations.

Use transactions and concurrency controls where needed to avoid partially approved or inconsistent content states.

- Marketing promotions and offer management — **Phase 12**.
- Advanced marketing budget management — **Phase 12**.
- Campaign attribution, conversion tracking, and ROI analytics — **Phase 13**.
- A generic advanced bulk-operation framework — **Phase 14**.
- Advanced cross-module workflow orchestration — **Phase 15**.
- A generalized external integration marketplace or public developer platform — **Phase 16**.
- Advanced business intelligence — **Phase 17**.
- AI-generated content, AI copywriting, predictive content optimization, or AI-assisted marketing — **Phase 18**.
- A new CRM or customer/contact management system.
- A duplicate campaign or delivery management system.

- A duplicate approval engine.

Do not implement future-phase functionality prematurely.

## 22. Recommended Implementation Sequence

Proceed in the following order:

1. Inspect the repository and document existing asset, document, approval, campaign, and delivery infrastructure.
2. Identify supported content formats and storage dependencies.
3. Define asset, template, version, approval, and campaign-content relationships.
4. Implement the secure asset library and file-handling workflow.
5. Implement asset metadata, categorization, and versioning.
6. Implement reusable templates and content authoring.
7. Implement safe template variables and rendering.
8. Implement preview and channel-specific validation.
9. Integrate the existing approval framework with immutable content versions.
10. Implement campaign-specific content instances and stable asset references.
11. Integrate validated content with Phase 10 provider adapters.
12. Implement optional localization support where justified.
13. Build library, editor, preview, approval, and campaign-content interfaces.
14. Add authorization, audit, operational safeguards, and documentation.
15. Run unit, integration, security, and regression tests.
16. Review for unsafe uploads, content injection, mutable approved content, broken asset references, and scope creep.

Adapt this sequence to the repository's architecture while preserving the acceptance criteria.

## 23. Acceptance Criteria

Phase 11 is complete only when the following criteria are satisfied or explicitly documented as blocked by verified repository limitations:

- [ ] Authorized users can upload, organize, search, preview, and manage supported marketing assets.
- [ ] File handling enforces size, type, access, and storage-security requirements.
- [ ] Asset versions preserve historical references.
- [ ] Authorized users can create, edit, reuse, and archive marketing templates.
- [ ] Template variables use a controlled allowlist and safe rendering rules.
- [ ] Missing required variables and invalid content are detected before delivery.
- [ ] Channel-specific validation uses existing Phase 10 capabilities where available.
- [ ] Content approval is tied to an immutable version.
- [ ] Approved and scheduled campaign content cannot be silently altered by later template edits.
- [ ] Campaign-specific content can reference reusable templates and assets.
- [ ] Phase 10 can obtain validated content and stable version references without duplicating delivery functionality.
- [ ] Previews do not trigger real external communications.
- [ ] Permissions, tenant isolation, auditability, and privacy controls are enforced.
- [ ] Asset and template references remain consistent through archival and version changes.
- [ ] Automated tests cover content validation, security, versioning, approvals, and integration.
- [ ] Documentation covers formats, storage, workflows, permissions, configuration, and limitations.
- [ ] Phases 01–10 continue to function.
- [ ] No duplicate CRM, campaign, delivery, document, or approval module has been created.
- [ ] No Phase 12 or later functionality has been implemented prematurely.

## Final Instruction

Implement **Phase 11 only**. Begin by inspecting the actual repository and Phases 01–10. Make real code changes where the coding environment permits, reuse established infrastructure, run available tests, and report results honestly.

Prioritize secure asset handling, safe content rendering, immutable versions, reliable approvals, and compatibility with existing channel integrations.

The result must be a production-oriented, industry-agnostic marketing asset and content management capability ready for **Phase 12: Promotions, Offers, and Campaign Budgets**, without prematurely implementing later phases.
