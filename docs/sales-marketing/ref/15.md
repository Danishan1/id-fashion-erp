# Phase 15: Sales & Marketing Workflow Integration

## 1. Objective

Implement a production-oriented, industry-agnostic **Sales & Marketing Workflow Integration** capability that coordinates existing business processes across Sales & Marketing and connected ERP modules.

The implementation must connect existing capabilities from Phases 01–14 into reliable, traceable workflows that can respond to business events, execute authorized actions, manage approvals, handle exceptions, and recover from failures.

The objective is to coordinate existing modules rather than duplicate their responsibilities.

The solution must support appropriate workflows involving:

- Sales enquiries and quotations.
- Pricing and discount approvals.
- Sales Order conversion and status synchronization.
- Sales targets and performance monitoring.
- Sales forecasting and commission-related events.
- Marketing campaigns and approvals.
- Audience segmentation and campaign execution.
- Content approvals and publication readiness.
- Promotions and campaign budgets.
- Campaign attribution and performance processing.
- Bulk processing and reconciliation.
- Existing Finance, CRM, identity, notification, and task-management services.

Use the existing workflow engine, approval framework, event bus, background jobs, notifications, and authorization system wherever available.

Keep all workflows industry-agnostic.

**Critical principle:** a workflow coordinates authoritative module operations. It must not become a second source of truth for quotations, orders, financial transactions, campaign delivery, permissions, or other module-owned records.

   - Workflow orchestration.
   - Approval requests and approval policies.
   - State machines and lifecycle transitions.
   - Domain events and event subscriptions.
   - Background jobs and scheduled execution.
   - Shared bulk processing.
   - Notifications and task assignments.
   - CRM and customer records.
   - Quotation and pricing services.
   - Sales Order conversion and status synchronization.
   - Sales targets, forecasts, commissions, and incentives.

   - Audit logs, authorization, tenant isolation, and observability.
4. Determine which capabilities already exist and which integration gaps are real.
5. Map the canonical source of truth, lifecycle ownership, permissions, and failure-recovery mechanism for every workflow to be implemented.

Do not introduce a separate workflow engine if a suitable one already exists. If no workflow engine exists, extend the repository’s existing event and job architecture with a small, durable orchestration layer rather than creating an unnecessarily broad general-purpose platform.

Integrate a useful set of real business workflows end to end.

Implement Phase 15 only.

## 4. Workflow Architecture

Define a workflow abstraction consistent with the existing architecture.

A workflow definition may include:

- Stable workflow identifier.
- Name and description.
- Version.
- Trigger event or explicit initiation method.
- Applicable tenant or organizational scope.
- Entry conditions.
- Workflow steps.
- Branching conditions.
- Approval requirements.
- Action handlers.
- Timeout and escalation rules.
- Retry policy.
- Failure-handling policy.
- Compensation strategy where applicable.
- Completion conditions.
- Permissions.
- Activation status.

A workflow instance should record:

- Workflow identifier and version.
- Business entity references.
- Tenant or organization reference.
- Current state and step.
- Creation and update timestamps.
- Trigger source and event identifier.
- Initiating user or authorized service identity.
- Approval and action references.
- Execution history.
- Retry and failure information.
- Correlation identifier.
- Completion or cancellation outcome.

Separate workflow definitions from workflow instances and execution history.

Do not store unrestricted executable code in workflow definitions. Actions must reference explicitly registered handlers with validated input schemas.

## 5. Workflow Lifecycle

Implement an explicit server-controlled workflow lifecycle.

Depending on the architecture, states may include:

- Draft.
- Active.
- Running.
- Waiting for approval.
- Waiting for an event.
- Scheduled or delayed.
- Retry pending.
- Completed.
- Rejected.
- Failed.
- Cancellation requested.
- Cancelled.
- Compensating.
- Completed with compensation failures.

Define legal transitions and validate them server-side.

Distinguish between a workflow being completed and an individual step being completed.

A workflow must not be marked complete while required actions or approvals remain unresolved.

Preserve execution history so authorized users can understand how the workflow reached its current state.

## 6. Event-Driven Integration

Reuse existing domain events and event infrastructure.

Create or extend event contracts for supported business transitions where required.

Potential events include:

- Enquiry created or qualified.
- Quotation submitted for approval.
- Quotation approved or rejected.
- Quotation accepted or expired.
- Sales Order conversion succeeded or failed.
- Sales Order status changed.
- Sales target updated or performance threshold reached.
- Commission calculation completed.
- Campaign submitted for approval.
- Campaign approved, scheduled, activated, or completed.
- Audience snapshot completed.
- Content version approved.
- Promotion activated or expired.
- Campaign budget threshold exceeded.
- Attribution calculation completed.
- Bulk job completed or failed.

Only emit events that accurately represent a committed state change.

### Event reliability

- Use the existing transactional outbox or equivalent mechanism where available.
- Otherwise, implement a repository-consistent durable publication mechanism where necessary.
- Include stable event identifiers, event types, timestamps, tenant context, and relevant canonical references.
- Version event contracts.
- Validate event payloads.
- Make event consumers idempotent.
- Handle duplicate, delayed, and out-of-order events.
- Avoid publishing success events before the underlying transaction commits.
- Avoid leaking sensitive information into event payloads.

Do not create duplicate event systems when the ERP already provides a suitable mechanism.

## 7. Workflow Triggers and Conditions

Support authorized workflow initiation through appropriate triggers:

- Domain events.
- Explicit user actions.
- Approved scheduled triggers.
- Completion of an existing bulk-processing job.
- Defined business thresholds.
- Other supported internal system events.

Conditions should be evaluated using typed, validated fields and registered predicates.

Examples include:

- Quotation value exceeds a configured approval threshold.
- A campaign is ready for approval.
- A campaign budget reaches a defined threshold.
- A required content version has not been approved.
- A supported sales performance threshold has been reached.
- A reconciliation job completes with exceptions.

Requirements:

- Use an allowlist of fields and operators.
- Validate types, ranges, and allowed values.
- Use safe query-building and parameterized database access.
- Prevent arbitrary SQL or script execution.
- Prevent conditions from accessing records outside the authorized tenant or scope.
- Define behavior for missing, stale, or unknown data.
- Reevaluate critical business conditions before executing consequential actions.

Do not allow workflow conditions to override authoritative module rules.

## 8. Approval Integration

Integrate with the existing approval framework.

If approval capabilities already exist, reuse their approval requests, policies, delegation, and audit mechanisms.

If no suitable framework exists, implement only the minimum reusable approval integration required for Phase 15.

Support appropriate approval scenarios, such as:

- High-value quotation or discount approval.
- Campaign approval.
- Promotion approval.
- Budget-change approval.
- Other explicitly authorized business actions.

Approval configuration may include:

- Approval policy or rule reference.
- Approver or authorized approver group.
- Threshold conditions.
- Sequential or parallel approval, if supported.
- Due dates.
- Escalation or reminder rules.
- Rejection behavior.
- Resubmission behavior.
- Approval history.

### Approval integrity

- Enforce separation of duties where required.
- Prevent unauthorized self-approval where policy prohibits it.
- Validate approver permissions at decision time.
- Record the decision, actor, timestamp, and relevant version.
- Prevent duplicate or conflicting decisions.
- Ensure approval applies to the correct record revision.
- Require reapproval when material fields change, according to the existing policy.
- Never treat a notification as an approval.
- Never treat workflow initiation as authorization to perform a protected action.

A workflow must call the authoritative business service after approval rather than directly changing protected fields.

## 9. Core Workflow Integrations

Implement a selected set of real workflows using the existing module services.

### Workflow A: Sales Enquiry to Approved Quotation

Coordinate the existing enquiry and quotation lifecycle.

Possible steps:

1. Detect a qualifying enquiry event.
2. Validate the relevant canonical CRM and enquiry references.
3. Assign or notify the authorized owner using existing assignment services.
4. Create or initiate a quotation draft only when explicitly supported by the existing quotation service.
5. Invoke existing pricing and discount calculations.
6. Determine whether approval is required.
7. Route the quotation to the existing approval mechanism.
8. Record approval, rejection, or resubmission.
9. Notify the appropriate users.
10. Complete the workflow when the defined terminal condition is reached.

Do not duplicate CRM entities, enquiry records, quotation records, or pricing calculations.

Do not auto-approve quotations merely because a workflow reaches an approval step.

### Workflow B: Accepted Quotation to Sales Order

Coordinate the existing Phase 04 conversion process.

Possible steps:

1. Detect an accepted-quotation event.
2. Verify the accepted quotation revision and required eligibility conditions.
3. Invoke the authoritative Sales Order conversion service.
4. Reconcile ambiguous responses before retrying.
5. Record the resulting canonical order reference.
6. Handle conversion failure or manual reconciliation requirements.
7. Notify authorized users.
8. Complete the workflow after confirmed conversion or an explicitly defined terminal exception.

Requirements:

- Preserve accepted commercial terms.
- Prevent duplicate orders.
- Reuse Phase 04 idempotency and recovery controls.
- Do not create Sales Orders directly from the workflow engine.
- Treat the Sales Order module as authoritative for order status.

### Workflow C: Marketing Campaign Readiness and Launch Coordination

Coordinate existing campaign, audience, content, budget, and delivery capabilities.

Possible steps:

1. Detect a campaign submitted for approval.
2. Validate the campaign lifecycle and required metadata.
3. Check that the intended audience or segment snapshot is ready.
4. Check that the intended content version is approved.
5. Check required budget or financial approvals.
6. Confirm applicable channel, consent, and suppression prerequisites.
7. Route outstanding approvals.
8. Verify that required prerequisites remain valid before execution.
9. Invoke the authoritative campaign or channel execution service when authorized.
10. Track the confirmed execution result and notify authorized users.

Do not interpret campaign approval as proof that messages have been sent.

Do not bypass the Phase 10 delivery safeguards, Phase 09 audience rules, Phase 11 content approvals, or Phase 12 promotion and budget controls.

Do not automatically launch campaigns unless the explicit workflow configuration and authorization permit it.

### Workflow D: Campaign Budget Exception

Coordinate Phase 12 budget records and existing notification or approval mechanisms.

Possible steps:

1. Detect an authoritative budget threshold or reconciliation event.
2. Verify the relevant campaign and budget references.
3. Create an exception or approval task.
4. Notify authorized budget owners.
5. Request a review or approval for supported corrective actions.
6. Invoke an authorized budget service only after the required decision.
7. Record the outcome and reconciliation status.

Do not modify financial records or initiate payments directly from the workflow engine.

Do not treat a forecast or estimate as an authoritative actual expenditure.

### Workflow E: Analytics and Reconciliation Completion

Coordinate existing Phase 13 and Phase 14 processing.

Possible steps:

1. Detect completion of a supported bulk job or attribution calculation.
2. Check whether the result completed successfully or contains exceptions.
3. Record the relevant source references and result summary.
4. Trigger an authorized follow-up reconciliation or reporting task.
5. Notify responsible users when exceptions require attention.
6. Retry only eligible, idempotent processing operations.
7. Complete when the configured success or exception-handling condition is satisfied.

Do not recalculate attribution by bypassing the Phase 13 engine.

Do not treat a bulk job's completion status as proof that all business data reconciled successfully.

### Workflow selection

Implement the workflows that fit the actual repository and existing modules. If a proposed workflow cannot be completed safely because a required service is missing, document the gap and implement only the supported integration boundary.

## 10. Step Types and Action Handlers

Provide reusable, registered step types as needed.

Potential step types include:

- Invoke an internal business service.
- Request approval.
- Send a notification through an existing service.
- Create a task.
- Wait for a specified duration.
- Wait for a defined domain event.
- Evaluate a validated condition.
- Start an approved bulk job.
- Record a business reference.
- Route to a failure or compensation handler.
- Complete or terminate a workflow.

Each handler must define:

- Input schema.
- Required permission.
- Idempotency behavior.
- Timeout behavior.
- Retryability.
- Side-effect classification.
- Result schema.
- Audit requirements.
- Compensation behavior, if supported.

Reject unknown or unregistered step types.

Do not implement arbitrary HTTP calls, unrestricted scripting, or arbitrary SQL as general workflow actions.

Generalized external integration capabilities remain part of Phase 16.

## 11. Durable Orchestration and Recovery

Workflow execution must survive worker restarts, deployment interruptions, and transient failures.

Requirements:

- Persist workflow state and step progress.
- Record completed and pending steps.
- Use idempotency keys for actions.
- Prevent concurrent workers from executing the same non-repeatable step unsafely.
- Resume from a durable checkpoint.
- Apply bounded retries and backoff.
- Distinguish transient from permanent failures.
- Handle late and duplicate events.
- Track timeouts and unresolved waits.
- Support manual recovery by authorized operators.
- Preserve execution and failure history.

Avoid keeping critical workflow state only in process memory.

### External and ambiguous outcomes

If an external action times out after submission, reconcile its outcome before retrying.

Do not assume a failed response means the action failed.

For example, an uncertain Sales Order conversion must be reconciled through Phase 04 before another conversion attempt.

## 12. Compensation and Partial Failure

Cross-module workflows cannot generally rely on one database transaction covering every step.

Implement explicit compensation only where the business operation has a safe, supported reversal.

Examples may include:

- Releasing a reserved resource through its authoritative service.
- Cancelling an eligible pending action.
- Reversing a supported temporary assignment.
- Marking a workflow for manual reconciliation when no safe compensation exists.

Do not automatically delete or reverse:

- Issued quotations.
- Confirmed Sales Orders.
- Posted financial records.
- Delivered marketing messages.
- Completed external transactions.
- Other irreversible business outcomes.

A compensation step is a new business operation, not a guarantee that the original action never happened.

Record compensation attempts and outcomes. If compensation fails, surface the workflow as requiring intervention.

## 17. Security, Audit, and Observability

### Security

Enforce:

- Tenant isolation.
- Role- and resource-based permissions.
- Workflow-definition administration permissions.
- Approval authority and separation of duties.
- Validation of event origin and payload.
- Protection against forged event triggers.
- Restrictions on sensitive workflow inputs and outputs.
- Authorization for retry, cancellation, and exception resolution.

Revalidate critical permissions when an action executes, not only when the workflow starts.

### Audit

Audit material events, including:

- Workflow activation and version changes.
- Workflow initiation.
- Approval decisions.
- Consequential business actions.
- Retries and manual recovery.
- Cancellation.
- Compensation.
- Exception resolution.
- Failed authorization attempts where appropriate.

Record the actor, timestamp, workflow version, step, result, and relevant canonical references.

### Observability

Provide operational metrics for:

- Running and waiting workflows.
- Completion and failure rates.
- Approval wait duration.
- Retry counts.
- Timeouts.
- Failed compensations.
- Queue latency.
- Workflows requiring intervention.
- Event-processing lag.

Use correlation identifiers to trace events, workflow instances, jobs, and business operations across modules.

Avoid logging credentials or unnecessary personal data.

## 19. Explicitly Out of Scope

Do not implement:

- Duplicate CRM, quotation, order, finance, campaign, or analytics modules.
- A second approval system when an appropriate one already exists.
- A second queue or job scheduler.
- A generic arbitrary-code workflow engine.
- A generalized public integration platform — Phase 16.
- Advanced enterprise BI — Phase 17.
- AI-generated workflow decisions or optimization — Phase 18.
- Automatic financial posting, payment execution, or unsupported reversals.
- Automatic campaign delivery that bypasses Phase 10 controls.
- Unrestricted external HTTP or executable-script workflow actions.
- Unrelated bulk-processing features already covered by Phase 14.

Do not implement later-phase functionality prematurely.

- [ ] Workflow definitions and instances are versioned and durable.

- [ ] Supported workflows can start from authorized events or explicit user actions.
- [ ] Event handling is idempotent and robust to duplicate delivery.
