# Phase 14: Shared Bulk Operations and Advanced Processing

## 1. Objective

Implement a reusable, production-oriented **Shared Bulk Operations and Advanced Processing** framework for the existing, industry-agnostic ERP Sales & Marketing module.

The framework must support safe, scalable, observable, and auditable processing of large collections of records across existing Sales & Marketing capabilities.

It should provide a common foundation for bulk operations such as:

- Importing records.
- Exporting authorized data.
- Bulk updates.
- Bulk validation.
- Bulk assignment.
- Bulk status transitions where permitted.
- Batch recalculation.
- Data reconciliation.
- Scheduled processing.
- Retriable background jobs.
- Processing reports and error exports.

The objective is not to build every possible bulk action. Build the shared infrastructure, then integrate a carefully selected set of existing Phase 01–13 operations to demonstrate that the framework works end to end.

**Critical principle:** shared processing infrastructure must orchestrate existing business operations, not bypass or duplicate their validation, permissions, workflows, financial rules, or authoritative data sources.

Keep the solution industry-agnostic. Do not introduce garment-, textile-, manufacturing-, or other industry-specific assumptions.

5. Document current capabilities and gaps before choosing an implementation approach.

If a capability already exists, extend it rather than rebuilding it.

## 4. Shared Bulk Operation Architecture

Design a common processing abstraction that individual modules can register and invoke.

A bulk operation should define:

- A stable operation type or handler identifier.
- A human-readable name and description.
- The supported input schema.
- The target entity or operation scope.
- Required permissions.
- Validation rules.
- Whether dry-run execution is supported.
- Whether the operation is reversible or compensatable.
- Whether partial success is allowed.
- Chunk size or processing limits.
- Idempotency requirements.
- Retry policy.
- Result and error reporting format.
- Audit requirements.

Use the existing application architecture for dependency injection, services, handlers, validation, and background jobs.

Do not build a generic arbitrary-code execution engine. Only explicitly registered and authorized operation handlers may execute.

### Recommended architecture

Separate the following responsibilities:

- Operation registration and configuration.
- Request validation.
- Job creation and persistence.
- Queue dispatch.
- Chunk planning.
- Chunk execution.
- Business-rule validation.
- Result aggregation.
- Retry and recovery.
- Cancellation handling.
- Audit and event publication.
- User-facing progress and error reporting.

Avoid putting the complete processing workflow into a single API controller or oversized service.

## 5. Operation Lifecycle and State Machine

Implement an explicit server-controlled lifecycle appropriate to the repository, potentially including:

- Draft or prepared.
- Validating.
- Validation completed.
- Awaiting approval, where required.
- Queued.
- Running.
- Cancellation requested.
- Cancelled.
- Completed.
- Completed with errors.
- Failed.
- Partially completed.
- Expired, where applicable.

Define legal state transitions and enforce them server-side.

Do not allow clients to mark jobs completed, override results, or arbitrarily change processing states.

Distinguish between:

- Validation failure.
- Execution failure.
- Partial success.
- User cancellation.
- System interruption.
- Retryable error.
- Permanent error.

A job must not be marked successful if required work remains incomplete.

Document the exact lifecycle implemented.

- Creation and submission timestamps.
- Start and completion timestamps.
- Current status.
- Total item count, when known.
- Validated item count.
- Successful item count.
- Failed item count.
- Skipped item count.
- Retry count.

Use secure storage for large input files and detailed results rather than storing unlimited payloads in a single database record.

## 7. Chunked and Asynchronous Processing

Support processing large jobs in bounded chunks.

Requirements:

- Avoid loading the entire input file or dataset into application memory.
- Use streaming or bounded pagination where appropriate.
- Use configurable chunk sizes with safe defaults and maximum limits.
- Reuse the existing queue and worker architecture.
- Apply backpressure when the system is under load.
- Respect database connection and provider rate limits.
- Prevent uncontrolled concurrent jobs from exhausting system resources.
- Persist progress at suitable checkpoints.
- Allow safe resumption after a worker restart.
- Ensure completed chunks are not processed again unintentionally.
- Preserve tenant context and authorization context throughout processing.

Chunk sizes and concurrency limits must be configurable within safe operational bounds.

Do not claim support for unlimited processing volumes. Document tested limits and any infrastructure requirements.

## 8. Validation and Dry-Run Preview

Where the operation supports it, provide a validation-only or dry-run mode before making changes.

A dry run should:

- Parse and validate input.
- Check field formats and required values.
- Check references to existing canonical records.
- Check applicable business rules.
- Check permissions and tenant boundaries.
- Detect duplicate or conflicting entries.
- Report items expected to succeed, fail, or be skipped.
- Provide a summary and downloadable validation report when appropriate.
- Avoid committing business changes or external side effects.

Clearly distinguish validation results from guaranteed execution outcomes. Records or permissions may change between validation and execution.

For operations that cannot be safely simulated, explicitly indicate that dry-run mode is unsupported or limited.

Require revalidation of critical conditions during actual execution.

## 9. Idempotency and Duplicate Prevention

Bulk processing must be safe under retries, duplicate submissions, worker restarts, and ambiguous failures.

Implement appropriate idempotency controls using stable job, item, source, and operation identifiers.

Requirements:

- Prevent duplicate job creation for a repeated request where idempotency is required.
- Prevent duplicate business changes when a chunk is retried.
- Persist per-item completion or equivalent durable checkpoints.
- Handle worker crashes between a business operation and progress recording.
- Reconcile uncertain outcomes before retrying non-idempotent actions.
- Avoid duplicate event publication where the architecture supports transactional outbox or equivalent guarantees.
- Enforce unique constraints at the database level where appropriate.

Do not assume that a job is safe to retry simply because the queue supports retries.

### External side effects

For provider calls, messages, financial operations, and other external side effects:

- Reuse existing idempotency keys and provider reconciliation mechanisms.
- Respect provider rate limits.
- Reconcile ambiguous timeouts before resubmitting.
- Do not promise exactly-once execution unless the underlying system genuinely supports it.
- Clearly document delivery or execution guarantees.

## 10. Retry, Recovery, and Failure Handling

Implement configurable retry policies appropriate to each operation.

Support:

- Transient network errors.
- Temporary provider failures.
- Rate-limit responses.
- Temporary database or infrastructure failures.
- Worker interruption.
- Permanent validation failures.
- Authorization failures.
- Business-rule conflicts.

Use bounded retries with appropriate backoff and jitter where supported.

Do not repeatedly retry permanent failures.

For partially completed jobs:

- Preserve completed work.
- Record failed items and reason codes.
- Resume only work that remains safe to execute.
- Allow authorized users to retry eligible failures.
- Avoid restarting successful items unnecessarily.
- Provide a clear distinction between retrying failed items and rerunning the entire operation.

Use a dead-letter or failed-job mechanism if supported by the existing architecture. Otherwise, implement a durable equivalent consistent with project conventions.

## 11. Cancellation and Concurrency Control

Support cancellation for eligible long-running jobs.

Requirements:

- A cancellation request must be recorded durably.
- Workers must check cancellation at safe checkpoints.
- Prevent new chunks from starting after cancellation has been recognized.
- Allow already-committed transactions to remain committed unless a supported compensation mechanism exists.
- Report partial completion accurately.
- Do not imply that cancellation automatically reverses prior changes.

Use concurrency controls to prevent conflicting bulk jobs from corrupting data.

Where needed, implement locks or conflict detection scoped to the relevant tenant, entity, or operation.

Prevent a single tenant or user from monopolizing shared worker capacity.

Respect established database locking and transaction conventions.

## 12. Bulk Import Framework

Build reusable import capabilities for supported entities that already exist.

Potential import targets should be selected based on actual repository support, for example:

- Sales enquiries.
- Quotation drafts.
- Campaign metadata.
- Audience or segment configuration metadata.
- Approved content metadata.
- Other suitable, non-financial records with stable schemas.

Do not import into every module automatically. Choose a small, useful set of targets for initial integration.

### Import requirements

- Support approved file formats already used by the project, such as CSV or XLSX.
- Validate file type, size, encoding, headers, row count, and schema version.
- Provide field mapping when useful and supported.
- Validate required fields and field types.
- Validate references against authoritative existing records.
- Enforce business rules and permissions.
- Detect duplicate records and conflicting identifiers.
- Provide dry-run validation.
- Support configurable create-only, update-only, or upsert behavior where appropriate.
- Use explicit matching rules for updates.
- Avoid accidental overwrites caused by weak matching.
- Produce row-level success, skip, and failure results.
- Securely store source files and validation reports.
- Apply retention and deletion policies.

### Import safety

Treat uploaded files and their contents as untrusted.

Protect against:

- Oversized files.
- Malformed CSV or spreadsheet data.
- Formula injection in generated exports.
- Path traversal.
- Unexpected file types.
- Unsafe archive expansion, if archives are supported.
- Spreadsheet parsing vulnerabilities.
- Malicious or oversized cell content.
- Cross-tenant reference injection.
- Unauthorized mass updates.

Never execute formulas, macros, scripts, or arbitrary code supplied in an import file.

Do not import credentials or overwrite protected system fields.

Use the existing file scanning mechanism if available; do not claim malware scanning exists if it is not configured.

## 13. Bulk Export Framework

Implement reusable, permission-aware export processing.

Support exports of approved datasets from selected existing Sales & Marketing modules.

Requirements:

- Reuse existing report queries and authorization rules.
- Apply tenant and row-level access restrictions.
- Enforce field-level permissions for sensitive data.
- Support bounded filters, date ranges, and pagination.
- Generate large exports asynchronously.
- Stream data where practical.
- Support appropriate formats, such as CSV or XLSX, based on existing libraries.
- Record export status and completion.
- Provide a secure, time-limited download mechanism consistent with the repository.
- Prevent unauthorized users from accessing another user's or tenant's export.
- Apply retention and cleanup policies.
- Audit sensitive or high-volume exports.

Protect exported CSV and spreadsheet cells against formula injection.

Do not bypass existing report permissions or expose fields merely because they exist in the database.

For person-level CRM data and financial data, apply stricter access controls where required.

## 14. Bulk Update, Assignment, and Status Operations

Provide reusable mechanisms for bulk changes, but keep business-specific logic inside each module's authoritative services.

Potential supported operations include:

- Assigning records to authorized users or teams.
- Updating permitted metadata fields.
- Applying approved classifications or tags.
- Executing supported status transitions.
- Recalculating eligible records through existing calculation services.

For each operation:

- Define permitted fields and transitions.
- Validate the complete request.
- Enforce authorization at both job and item level.
- Revalidate critical business rules during execution.
- Preserve field-level and entity-level validation.
- Apply optimistic concurrency or conflict detection where appropriate.
- Record item-level results.
- Audit material changes.
- Avoid updating protected fields or bypassing approval workflows.

Do not implement generic mass assignment that allows clients to modify arbitrary entity properties.

Do not bypass the quotation approval lifecycle, promotion eligibility rules, attribution integrity, or other established business controls.

## 21. Security, Authorization, and Audit

Enforce:

- Tenant isolation at job, item, file, and result levels.
- Permission checks when jobs are created.
- Item-level authorization and business validation during execution.
- Permission checks when viewing, retrying, cancelling, or downloading results.
- File access controls and safe storage.
- Protection against unauthorized job identifier enumeration.
- Safe handling of uploaded files.
- Rate limits and abuse prevention.
- Audit records for high-impact operations.
- Retention and deletion controls.

Do not assume that a user who was authorized when a job was submitted remains authorized indefinitely. Revalidate permissions when required by the operation's risk and the existing authorization model.

Where a user's access is revoked, define whether queued work is cancelled, blocked, or allowed to continue under an explicitly authorized service identity.

Do not use a service identity to bypass tenant boundaries or business authorization.

## 22. Transactions and Consistency

Define transaction boundaries carefully.

For each operation, determine whether it supports:

- One transaction per item.
- One transaction per chunk.
- A larger atomic transaction.
- Partial success.
- Compensation for previously completed work.

Do not promise whole-job atomicity when processing spans multiple chunks, external providers, or independently committed records.

Where partial success is allowed, report it accurately.

For operations with dependencies between items, define processing order or dependency resolution explicitly.

For external side effects, use the existing outbox, idempotency, and reconciliation mechanisms where available.

For irreversible operations, require appropriate confirmation and potentially additional authorization.
