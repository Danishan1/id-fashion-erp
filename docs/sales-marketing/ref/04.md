# Phase 04: Sales Order Integration

## 1. Role and Objective

Act as a senior ERP architect, full-stack engineer, database engineer, and QA engineer.

Implement **Phase 04: Sales Order Integration** in the existing ERP repository.

The ERP is designed for multiple industries and business models. All functionality must remain industry-agnostic and configurable.

The primary objective is to connect the existing Sales & Marketing workflows with the existing Sales Order Management module so that authorized users can convert accepted quotations into valid sales orders, manage conversion exceptions, track order status, and maintain traceability across the entire commercial lifecycle.

This phase is an integration phase, not an instruction to build a new Sales Order Management system.

2. The Sales & Marketing Feature Requirements Document.
3. Phase 01 foundation implementation.

11. Existing APIs, frontend routes, tests, and database migration conventions.

Search the full repository for order creation, quotation conversion, order confirmation, order approval, and existing integrations before implementing anything.

### Mandatory reuse rules

- Reuse the existing Sales Order Management module.
- Reuse its authoritative order creation service and lifecycle.
- Reuse existing order numbering and validation.
- Reuse the existing pricing engine from Phase 03.
- Reuse quotation revision and acceptance records from Phase 02.
- Reuse existing customer, product, tax, currency, and address data.
- Reuse existing inventory, fulfillment, finance, and shipping integrations where available.
- Reuse existing permissions, audit logs, events, and notifications.
- Do not create duplicate sales order, order line, customer, product, invoice, or payment tables.
- Do not bypass existing order approval or validation rules.
- Do not implement downstream fulfillment, invoicing, or accounting functionality that belongs to other modules.
- If an equivalent integration already exists, verify and improve it instead of creating a parallel workflow.

If Sales Order Management is absent, do not fabricate a complete order system. Implement a clearly defined integration contract, document the missing dependency, and build only the smallest adapter justified by the existing architecture.

## 4. End-to-End Business Workflow

Implement the following integration flow:

1. A sales enquiry is created and managed through the existing enquiry workflow.
2. A quotation is created and priced through the existing quotation and pricing services.
3. The quotation follows the required review and approval process.
4. The quotation is issued to the customer.
5. The customer accepts a specific quotation revision through a supported and auditable method.
6. The system validates that the accepted revision is eligible for conversion.
7. The system validates the required customer, product, currency, tax, commercial, and order data.
8. The system creates the Sales Order through the existing authoritative order service.
9. The system records the resulting order reference against the originating quotation and accepted revision.
10. The system records conversion history and emits appropriate events.
11. The Sales & Marketing interface displays the linked order and its current status.
12. Later order lifecycle updates are reflected through existing APIs or events without duplicating order state.

The workflow must remain consistent if a request is retried, a network call fails, or two users attempt conversion concurrently.

## 5. Conversion Eligibility

Create a centralized backend service to determine whether a quotation revision can be converted.

Validate at least the following, where applicable:

- The quotation exists and belongs to the current organization or tenant.
- The user has permission to convert quotations.
- The quotation has an explicitly recorded customer acceptance.
- The accepted revision matches the revision being converted.
- The quotation is not cancelled, expired, rejected, or superseded.
- The accepted revision has not already been converted into an order.
- The customer or account is valid and accessible.
- Required customer and order details are available.
- Every referenced product or service is valid and orderable.
- Quantities and units are valid.
- Currency and required commercial fields are compatible with the order model.
- Pricing and tax information satisfy the existing order service's requirements.
- Any required approval has been completed.
- The existing Sales Order module's own validation rules pass.

Do not duplicate all order validation rules inside the integration. Perform early checks where helpful, then invoke the authoritative order service, which must remain responsible for order validity.

Return actionable validation errors to the user.

Do not allow a quotation's internal approval status to be mistaken for customer acceptance.

## 6. Commercial Data Mapping

Create an explicit, documented mapping from the accepted quotation revision to the existing Sales Order model.

Map the fields supported by both modules, including where applicable:

### Order header

- Customer or account reference.
- Customer contact reference.
- Bill-to and ship-to references.
- Currency.
- Exchange-rate reference where supported.
- Order date.
- Requested delivery or service date.
- Applicable payment terms.
- Applicable delivery or service terms.
- Customer purchase order reference, if provided.
- Sales channel or sales representative references, if supported.
- Customer-facing notes.
- Relevant shipping or service information.
- Source quotation reference.
- Source quotation revision.
- Source enquiry reference where supported.

### Order lines

- Product or service reference.
- Description.
- Quantity.
- Unit of measure.
- Agreed unit price.
- Discount information.
- Tax category and tax data as supported by the order model.
- Line total or other calculated fields accepted by the order service.
- Requested delivery or service details.
- Relevant customer item references, if supported.

### Mapping rules

- Use the accepted revision, not the latest editable quotation draft.
- Do not map arbitrary fields directly into the database without invoking the order service.
- Do not trust client-submitted prices, totals, discounts, or tax amounts.
- Preserve the accepted commercial terms and source references.
- Use Phase 03 pricing snapshots and the existing order service's rules for any necessary validation or transformation.
- Do not silently replace accepted prices with current price-list values.
- Do not silently recalculate a historical accepted quotation using today's pricing rules.
- If the order module requires fields absent from the quotation, obtain them through existing master data or request explicit user input where appropriate.
- Never fabricate missing commercial data.

If the existing Sales Order model cannot preserve a required historical commercial value, document the gap and implement the smallest safe integration solution.

## 7. Pricing and Tax Consistency

The accepted quotation is the authoritative commercial agreement for the conversion, subject to existing order rules and applicable legal or business constraints.

Requirements:

- Preserve the accepted revision's prices and discounts.
- Preserve the source currency and relevant exchange-rate context where applicable.
- Maintain traceability to the pricing snapshot and rule versions.
- Reuse the existing tax engine and order calculation service.
- Ensure the order total is consistent with the accepted quotation under the ERP's documented rounding and tax rules.
- If the order module legitimately applies additional calculations, identify those calculations and validate the outcome before completing conversion.
- If the order module cannot preserve the accepted terms, fail safely and report the discrepancy instead of silently creating a commercially different order.
- Do not automatically reprice an accepted quotation against newly activated price lists.
- Do not introduce a second pricing or tax engine.

Any allowed discrepancy must be explained, validated, and auditable according to existing business policy.

## 8. Idempotency and Duplicate Prevention

This is a critical requirement.

The conversion operation must be safe to retry and resistant to concurrent requests.

Requirements:

- Assign a stable conversion operation identifier or use the existing idempotency mechanism.
- Enforce a database-level uniqueness constraint or equivalent transactional guarantee preventing duplicate conversion of the same accepted quotation revision.
- Check for an existing successful conversion before creating another order.
- Protect against simultaneous conversion requests.
- Handle retries after timeouts when the original order may already have been created.
- Return the existing linked order when a repeated request represents the same completed conversion.
- Distinguish a retry of the same conversion from a legitimate new business operation.
- Do not create a second order because the client did not receive the first response.
- Avoid relying only on a frontend button being disabled.
- Use transactions, locks, idempotency keys, or other mechanisms supported by the existing architecture.

If order creation and conversion-record persistence cannot be completed in one database transaction, implement a reliable recovery strategy that reconciles the conversion record with the order service. Do not assume distributed operations are atomic.

## 9. Conversion Lifecycle and Error Handling

Represent the integration status using the existing workflow conventions.

If no suitable lifecycle exists, use a minimal conversion-state model such as:

- Not Eligible
- Ready for Conversion
- Processing
- Converted
- Failed
- Reconciliation Required

Do not confuse conversion status with quotation status or Sales Order status.

Requirements:

- A conversion attempt must record its initiation.
- Successful conversion must record the resulting order reference.
- Failed conversion must record a safe, actionable error.
- Retryable failures must be distinguishable from permanent validation failures.
- Retrying must not create duplicate orders.
- If the outcome is uncertain because of a timeout or partial failure, reconcile before attempting another order creation.
- Failed conversions must not mark the quotation as successfully converted.
- Conversion history must preserve relevant attempts and outcomes.
- Recovery operations must be authorized and auditable.

Do not automatically reopen or alter customer acceptance merely because order creation failed.

## 11. Order Status Synchronization

Sales & Marketing should display the current order status without becoming a competing source of truth.

Requirements:

- Reuse existing order APIs or domain events.
- Display the authoritative order status.
- Maintain source links between enquiry, quotation, revision, and order.
- Avoid copying the entire order state into Sales & Marketing.
- If a minimal local status snapshot is required for performance, define how it is refreshed and how stale values are identified.
- Handle order cancellation, closure, rejection, and other state changes consistently with existing business rules.
- Do not automatically change a quotation's acceptance status when the order changes status.
- Do not infer fulfillment or payment completion from order creation alone.

- Prevent cross-tenant quotation and order access.
- Validate that linked CRM, customer, and order records belong to the authorized tenant.
- Prevent unauthorized conversion of unaccepted quotations.
- Prevent unauthorized modifications to accepted quotation revisions.
- Prevent users from bypassing order approval requirements.
- Restrict access to order details according to existing permissions.
- Validate all input fields.
- Avoid insecure direct-object references.
- Never trust frontend eligibility results.
- Do not expose secrets, credentials, or sensitive error details.
- Ensure retries cannot bypass authorization or business rules.

## 19. Acceptance Criteria

Phase 04 is complete when applicable criteria are met:

1. An authorized user can determine whether an accepted quotation revision is eligible for conversion.
2. An eligible accepted quotation can create a Sales Order through the existing order service.
3. The order contains the correct customer, lines, quantities, currency, and accepted commercial terms.
4. The order retains a traceable link to the originating quotation and revision.
5. The system prevents duplicate conversion during retries and concurrent requests.
6. Conversion failures are recorded and can be safely diagnosed and recovered.
7. Uncertain outcomes are reconciled before another order is created.
8. Sales & Marketing displays the linked order and its authoritative current status.
9. Existing order approval and validation rules remain enforced.
10. Conversion actions are permission-controlled and auditable.
11. Relevant events and notifications are published reliably.
12. Tenant isolation is enforced.
13. Tests cover successful conversion, failure recovery, concurrency, and security.
14. Existing Sales Order and quotation workflows remain operational.
15. No duplicate Sales Order Management module has been introduced.
16. Documentation explains conversion mapping, idempotency, recovery, and integration behavior.

If a criterion depends on a missing module, document the dependency and implement a suitable integration boundary. Do not claim full operational integration where the required functionality is unavailable.
