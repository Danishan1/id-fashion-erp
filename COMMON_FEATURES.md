# Common Features & Reusable Assets Registry

This file is the **single source of truth for "does this already exist?"** — read it before starting any
new module, component, service, or utility. It complements `CLAUDE.md` (which tracks architecture and
phase history/decisions); this file tracks **what reusable building blocks already exist and how to use
them**, so nothing gets rebuilt or duplicated.

**Rule for every new module going forward** (see also the working-agreement note in project memory):
1. Check this file first for an existing component/service/utility that fits.
2. If something reusable is genuinely missing, build it generically (not hard-coded to one module) and add
   it here immediately.
3. Never leave a second, slightly-different implementation of something already listed below — extend the
   existing one instead.
4. Update this file in the same commit/session as the code that introduces or changes a reusable asset.
   Never delete an entry unless the asset itself is deleted from the codebase — mark it "Deprecated" instead
   if it's being phased out.

## 4. Backend module pattern (`src/modules/<name>/`)

Every domain module follows **schema → repository → service** (built in that order from day one for new
modules — this was retrofitted onto the earlier masters and should never need retrofitting again):

- `*.schema.ts` — Zod validation schemas.
- `*.repository.ts` — Prisma queries only, no business logic. Two shapes in use, pick per module's actual complexity:
  - **Rich repository** (named query methods: `findById`, `findByCode`, nested includes, dual-view filters) — use when the module has real query complexity (Customers, Suppliers, Employees, Warehouses, Products, Sampling).
  - **Thin re-export** (`export const XRepository = { entityA: prisma.entityA, entityB: prisma.entityB }`) — use for simple lookup tables with no query complexity beyond a duplicate-code check (garment-attributes, fabric-config, hr-config, production-config, cost-master, finance-config, lookups, departments).
- `*.service.ts` — business logic, state machines, RBAC assertions, audit logging. **Never imports `@/core/db/client` directly** — always goes through the sibling repository.
- `makeSimpleLookupService()` factory (in `garment-attributes.service.ts`) — generic CRUD-with-audit-and-tenant-check factory driving all 8 garment-attribute entities from one implementation. **Reuse/extend this factory pattern before hand-writing another near-identical simple-lookup service.**

**API routes** (`src/app/api/v1/<module>/...`): thin — parse/validate, call service, map errors via
`handleApiError`. Non-CRUD business operations are sub-resource POSTs
(`POST /api/v1/sampling/:id/resume`, not a generic status PATCH with a caller-chosen target).

**Pages** (`src/app/(dashboard)/<module>/...`): Server Component fetches data directly (no fetch
round-trip) and composes one or more Client Components for interactivity — established pattern:
`ProductForm`+`VariantsSection`, `CustomerForm`+`BuyersSection`, `WarehouseForm`+`LocationsSection`,
`SampleWorkflowPanel`. **Every stateful Client Component fed server data via props must receive
`key={id}`** (Next.js App Router does not remount on client-side navigation between different `[id]`
routes, and `useState(initial)` only runs on first mount — this was a real cross-cutting bug, now fixed
everywhere). When two sibling keyed components exist on the same page, use distinct prefixes
(`key={\`form-${id}\`}`, `key={\`variants-${id}\`}`) — React requires key-uniqueness among siblings, not
per component type.

## 5. Mandatory security pattern — tenant scoping

**Every by-id repository lookup must filter by `companyId`.** `findUnique({ where: { id } })` with no
company check is an IDOR (cross-tenant read/write) — this exact bug was found and fixed in 27 places across
8 modules in one session (Sampling's `addSampleMaterial`, plus 26 `update*` functions across
garment-attributes/fabric-config/hr-config/production-config/cost-master/finance-config/lookups). The
correct pattern everywhere:
```ts
const existing = await Repository.entity.findFirst({ where: { id, companyId: actor.companyId } });
if (!existing) throw new BusinessRuleError("NOT_FOUND", "...");
```
Apply this to **every new by-id lookup in every new module**, no exceptions — do not wait for an audit to
catch it.

## 6. Scoped single-field update sub-route pattern

Any time one field on a record needs its own edit lifecycle independent of the record's main
create/update flow — a quick isActive toggle from a list row, or a field that's editable at times the
main form doesn't cover (e.g. a transactional header field that stays editable after the record is
otherwise locked) — give it its **own dedicated sub-route that touches only that field**, never reuse the
full create/update endpoint. Examples in the codebase today:
- `PATCH /api/v1/<masters-module>/:id/status` — toggles `isActive` only (list row's projection doesn't carry every required FK the full schema validates — see Employee's list row example in `CLAUDE.md`).
- `PATCH /api/v1/sampling/:id/color` — lets `SampleRequest.color` stay editable at any status even though the header itself is otherwise immutable by identity fields (customer/style never change after create).
- `PATCH /api/v1/sampling/materials/:materialId/damage` — records `SampleMaterial.damagedQuantity`/`damageReason`, discovered after the material line already exists, not at planning time. **Gotcha to remember for the next Decimal field**: it comes back from the API as a *string* (Prisma JSON-serializes `Decimal`), so a display check must be `value !== null`, never a truthy check — a legitimately-recorded `0` is the string `"0"`, and while that happens to be truthy (so it wasn't the bug here), the truthy check is still wrong in general and did cause a real display bug once a value was cleared back toward zero. See `CLAUDE.md`'s dated note for the full story.

Each such route: its own tiny Zod schema, its own `update<Field>()` service function doing a
`companyId`-scoped existence check + `writeAuditLog`, and a `PATCH` handler mirroring `requireSession()` →
`PermissionService.assert()` → parse → service call → `handleApiError`. Reuse this shape for the next
one-off editable field rather than inventing a new pattern.

## 7a. Edit-after-create pattern for transactional headers with detail lines

For a header+detail(+sub-detail) transactional record (Sales Order → Items → Breakdown; will apply again to
BOM → BomItem, Production Order → its lines) that needs to stay editable past creation, and possibly past
one gated state transition:

- **Full replace over hand-diffing**: `<Module>Repository.replaceItems(headerId, headerData, items)` —
  inside one `prisma.$transaction`, delete existing detail(+sub-detail) rows for that header, then recreate
  from the submitted set, then update the header fields. Simpler and safer than diffing which lines
  changed/added/removed for a structure with no independent per-line lifecycle (unlike Sampling's
  append-only versions, which must never be edited/replaced). See `SalesOrderRepository.replaceItems()`.
- **Re-run any creation-time gate on edit, via one shared helper** — don't duplicate the gate's logic
  between the create/confirm path and the edit path. Extract it once (see
  `assertSamplesApprovedOrOverride()` in `sales-order.service.ts`, called from both `confirmSalesOrder()`
  and `updateSalesOrder()`) so an edit can't be used to sneak past a business rule a fresh create/confirm
  would have enforced.
- **Bound editability to a small explicit set of statuses**, not "anything non-terminal" — e.g. Sales
  Orders allow edit only in `DRAFT`/`CONFIRMED`, refusing once a later real-world commitment (Production)
  exists to consume the record's committed quantities. Throw `INVALID_STATE_TRANSITION` with a message that
  tells the user what to do instead ("create a new order") rather than just naming the blocked status.
- **UI**: reuse the same form component in a dual create/edit mode via an optional `initial<Entity>` prop
  (pre-fills every field including nested line/quantity state), submit branches `POST` vs `PATCH`. The
  blocked-by-gate → override UX on the edit form should mirror whatever the create/confirm flow already
  uses (amber notice, reason field, "confirm/save anyway" button) — one override UX per concept, not one
  per screen it appears on.

- **2026-08-21** — Every real (non-soft) delete button gets a `ConfirmModal` first — extended this to Sampling's Other Charge "Remove" and Attachment "Remove" (neither has a `deletedAt`/`isActive` column; both are genuine `prisma.*.delete()` calls, and attachment delete also removes the file from disk — nothing recoverable through the app). - **2026-08-21** — Purchase Request itself was superseded same-day by Material Request (Inventory-owned, no pricing, no approval gate) after a user-driven re-analysis of the actual procurement flow — see `CLAUDE.md`'s Material Request section for the full design. Two lessons worth generalizing beyond that one module: (1) **`prisma format` will silently synthesize a missing relation's opposite side** instead of erroring — a mechanical rename across several models (`purchaseRequestItems` → `materialRequestItems`) that didn't check whether the new item model actually had a matching field left one relation orphaned, and `format` quietly added a phantom column to paper over it. `prisma validate` (not `format`) is what actually catches this with a clear error; a stray unmapped camelCase column showing up in a generated migration's `CREATE TABLE` is the other tell. Run `validate` after any bulk rename across relation back-references, don't trust `format`'s silence as confirmation. (2) **A derived-state guard needs to be checked in every place the same guard matters, not just the service** — the service's real "has anything actually happened yet" check (`assertNothingIssuedOrEscalated`, keyed off real line data, not the status label) was correct from the start, but the Edit page's `notFound()` guard and the detail panel's Edit-link visibility both independently re-approximated it from the status label alone and were both wrong in the same way. When a service has a real-state guard beyond a simple status check, every UI surface that pre-empts calling that service (a page guard, a conditionally-rendered link/button) needs to derive the identical condition, not a simplified proxy for it.
